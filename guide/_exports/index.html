OpenShell Workload Identity with SPIFFE and SPIRE

2026-10-15

Overview

Start here

OpenShell is a runtime for autonomous AI agents, and it runs each agent in a sandbox, an isolated boundary around the agent’s processes. Agents often need to call APIs that expect an access token, and OpenShell usually grants that access with a stored credential. This guide sets up the alternative: each sandbox proves its workload identity, an identity issued to running software, and receives a short-lived access token from an OAuth2 token service in return. That only works if the token service trusts the identity and the identity names the right sandbox and nothing else. At the end, SPIRE, which identifies running workloads and issues identities to them, gives each sandbox a signed identity on OpenShift. Red Hat build of Keycloak, the token service, accepts that identity and issues an access token, and OpenShell adds the token to the agent’s requests to your API. With the OAuth2 client_credentials grant that this guide uses, OpenShell stores no credential for the API and sends no client secret.

What the parts are

OpenShell

A runtime for autonomous AI agents. Agents work with files, APIs, and credentials, and a policy that you declare for each agent sets what it may touch. Agents never see real credentials; OpenShell adds them only to requests bound for approved endpoints.

Sandbox

The isolated boundary an agent runs in. It owns the agent’s processes and forwards the agent’s network traffic.

Supervisor

The OpenShell process on the trusted side of the sandbox boundary, to which the sandbox forwards the agent’s network traffic. It checks requests against policy, supplies credentials, and opens approved connections. On Kubernetes, the supervisor has its own Pod, apart from the agent’s Pod.

Gateway

The OpenShell control plane: it manages the lifecycle of sandboxes, delivers policy and settings, and attaches providers. The supervisor loads its policy and provider state from the gateway.

Provider and token grant

A provider connects a service name to a stored credential, which the supervisor hands out only where policy allows it. A token grant is a provider flow that injects a short-lived access token instead. The supervisor sends the sandbox’s identity to an OAuth2 token service as the client assertion, the signed token that authenticates the client in place of a client secret. It injects the access token it receives into the requests that match the provider. With the client_credentials grant type, the supervisor sends the assertion straight to the token service. With the token_exchange grant type, the gateway first brokers an intermediate token for the supervisor.

SPIFFE

A standard for bootstrapping and issuing identity to services across heterogeneous environments. It names a workload with a SPIFFE ID, a URI of the form spiffe://<trust-domain>/<path>, where the trust domain names the system that issued the identity and the path names the workload. The identity document that SPIFFE defines is the SVID (SPIFFE Verifiable Identity Document). A JWT-SVID is a signed JWT whose sub claim is the SPIFFE ID of the workload it was issued to.

SPIRE

The SPIFFE runtime environment. It attests running software, which on Kubernetes means it identifies the Pod that calls it with information from the node’s kubelet. It then issues SPIFFE IDs and SVIDs to that software through the SPIFFE Workload API, the API through which workloads receive their SVIDs. A registration tells SPIRE which Pods receive which SPIFFE ID, as one registration entry per Pod.

Zero Trust Workload Identity Manager

An OpenShift operator that deploys and manages SPIRE. It runs the SPIRE server, and it runs the SPIRE agent as a DaemonSet. It also runs the SPIFFE CSI driver, which serves the agent’s Workload API socket to Pods as a volume, and the SPIRE OIDC discovery provider, which publishes the keys that verify JWT-SVIDs.

Red Hat build of Keycloak

Keycloak is open source identity and access management that adds authentication to applications and secures services. In this guide, the Red Hat build of Keycloak is the OAuth2 token service, the identity provider (IdP) that issues the access tokens. Its SPIFFE identity provider feature lets clients authenticate with SPIFFE JWT-SVIDs.

How they fit together

OpenShell mounts the Workload API socket that the SPIFFE CSI driver serves into the supervisor Pod; the Pod that runs the agent receives no identity socket. When the agent sends a request to an endpoint of a token grant provider, the supervisor intercepts it and looks for a cached access token. Without one, it fetches a JWT-SVID over the socket (step 1 in the diagram) and sends it to the Keycloak token endpoint as the client assertion (step 2). Keycloak looks up the one client whose SPIFFE ID matches the sub claim and verifies the signature with the keys that the SPIRE OIDC discovery provider publishes (step 3). Keycloak then returns an access token, which the supervisor caches (step 4). The supervisor injects the token into the agent’s request and forwards it to the protected API, the API your agent calls (step 5). With client_credentials, the gateway is not on this path; it supplies the supervisor’s policy and provider state.

How it works follows each step in detail.

Why this combination

The obvious alternative is a client secret stored in a provider. In this setup, each JWT-SVID is short-lived and is issued to one attested Pod instead. By default a JWT-SVID expires after five minutes, and a registration entry can set a different lifetime. The registration in this guide binds each of its entries to the UID of the supervisor Pod, so SPIRE serves the JWT-SVID only to that Pod. Keycloak’s federated client authentication removes the need to assign and manage a secret for each client, and with client_credentials the supervisor sends only its JWT-SVID. OpenShell also keeps the access token out of the sandbox environment. You install Zero Trust Workload Identity Manager and Keycloak through operators from the redhat-operators catalog, and OpenShell through its Helm chart.

The verified path

The end-to-end run used OpenShell 0.1.4, Zero Trust Workload Identity Manager 1.1.2, and Red Hat build of Keycloak 26.6.7. The token_exchange grant type was not verified. Status and limits

The SPIFFE identity provider is a preview feature of Keycloak and is not fully supported. Preview features are disabled by default, are not recommended for production, and may change or be removed in a future release.
What the identity proves

The Pod UID that binds a JWT-SVID to its Pod is not part of the SPIFFE ID. In the registration this guide creates, the sandbox part of the SPIFFE ID comes from a Pod annotation, and SPIRE does not attest annotations. The registration also requires the Pod name to be os-supervisor- followed by that annotation value, which ties the annotation to the name of the attested Pod. The sandbox part names the right sandbox only while untrusted users cannot create or patch Pods in the sandbox namespace. A restarted sandbox gets a new supervisor Pod with the same SPIFFE ID, so the SPIFFE ID names a sandbox, not one Pod. With client_credentials, the gateway never sees the JWT-SVID, and Keycloak’s client lookup is the only check on the full SPIFFE ID. With token_exchange, the gateway checks the issuer, audience, signature, and trust domain of the JWT-SVID, not the path of the SPIFFE ID. Trust model explains what the identity proves and why sandbox namespaces must stay administrative.

Token service

The setup depends on the Keycloak SPIFFE identity provider and its client assertion type urn:ietf:params:oauth:client-assertion-type:jwt-spiffe, so Red Hat build of Keycloak is the only token service it is known to work with.

One Keycloak client per sandbox

Because Keycloak resolves each sandbox’s SPIFFE ID to exactly one client, every new sandbox needs its own Keycloak client, and creating it is a step you must automate (Create a client for each sandbox).

Token checks at your API

OpenShell rejects token values that are unsafe for an HTTP header but does not validate the token for the target. The protected API must validate its issuer, audience, signature, and expiry and authorize requests by its azp claim, the Keycloak client it was issued for (Protect the target API).

How it works

This page follows one token grant from a sandbox to the API it protects. A token grant is the OpenShell provider flow in which the sandbox supervisor obtains a short-lived access token from an OAuth2 token service, using the sandbox’s SPIFFE JWT-SVID as the client assertion. The token service here is Keycloak, the identity provider (IdP). The page covers where the identity socket lives, the five steps of the client_credentials grant, and what the OpenShell gateway checks on a JWT-SVID.

A SPIFFE ID is a URI of the form spiffe://<trust-domain>/<path>. The trust domain names the system that issued the identity, and the path names the workload inside it. A JWT-SVID is a signed JWT whose sub claim is the SPIFFE ID of the workload it was issued to.

The two Pods of a sandbox

The OpenShell gateway is the control plane that manages the lifecycle of sandboxes. A sandbox is the boundary the agent runs in. It owns the agent’s processes and forwards the agent’s network traffic to the supervisor. The supervisor sits on the trusted side of that boundary: it checks requests against policy, supplies credentials, and opens approved connections.

On Kubernetes, the sandbox and the supervisor run in separate Pods. The workload Pod runs openshell-sandbox and the agent process. A second Pod, managed directly by the Kubernetes driver, runs openshell-supervisor. The supervisor authenticates to the gateway, loads policy and provider state, authorizes each destination, and opens the upstream connections. The driver creates a namespace-wide NetworkPolicy that denies all workload egress, so the agent’s traffic leaves the sandbox only through the supervisor.

Of the two Pods of a sandbox, only the supervisor Pod receives the identity socket. Zero Trust Workload Identity Manager runs the SPIRE agent and the SPIFFE CSI driver as DaemonSets, and the CSI driver serves the SPIRE agent’s Workload API socket to Pods as a volume. When the driver setting provider_spiffe_workload_api_socket_path is set, the driver adds a read-only csi.spiffe.io volume to the supervisor container, mounted at the socket’s parent directory. It also sets OPENSHELL_PROVIDER_SPIFFE_WORKLOAD_API_SOCKET to the socket path. An empty value disables the mount. The workload Pod receives no provider identity socket and no gateway credential. The Helm chart also mounts the socket into the gateway Pod, which uses it only for token_exchange.

The client_credentials sequence

Arrow 5 shows the agent’s request, which the supervisor holds from step 1 until it has a token, then forwards with the token injected.

  1. The supervisor fetches a JWT-SVID. The agent sends an HTTP request to an endpoint that a provider profile declares. The supervisor intercepts it and looks for a cached access token. On a cache miss, it requests a JWT-SVID from the SPIRE agent over the mounted Workload API socket. The JWT-SVID audience is jwt_svid_audience from the profile. Without that field, the supervisor derives the audience from the token endpoint: for a token endpoint whose path contains /realms/<realm>/, it keeps the part up to /realms/<realm>, and for other URLs it uses the full token endpoint.

  2. The supervisor sends the JWT-SVID as client assertion. The supervisor POSTs to token_endpoint with grant_type=client_credentials, client_assertion_type, and the JWT-SVID as client_assertion. The request carries no client_id and no client secret. OpenShell defaults client_assertion_type to urn:ietf:params:oauth:client-assertion-type:jwt-bearer. The Keycloak SPIFFE identity provider accepts only urn:ietf:params:oauth:client-assertion-type:jwt-spiffe, so a profile for Keycloak sets that value.

  3. Keycloak verifies the JWT-SVID. Keycloak looks up the client whose federated JWT credential subject equals the assertion’s sub, the SPIFFE ID. That client names the SPIFFE identity provider that verifies the assertion. The identity provider rejects a sub outside its configured trust domain. It accepts exactly one audience, the realm issuer URL <base>/realms/<realm>. For a Keycloak token endpoint, the audience the supervisor derives in step 1 has this same <base>/realms/<realm> form. It checks the signature with keys fetched by an HTTP GET on its bundle endpoint. This guide sets the bundle endpoint to the /keys endpoint of the SPIRE OIDC discovery provider, which serves the JSON Web Key Set for JWT validation.

  4. Keycloak returns an access token. The token endpoint answers with an access token. The supervisor caches it for cache_ttl when the profile sets one, and otherwise for the expires_in of the token response, at most one hour, minus 30 seconds. When the response gives no positive expires_in, the supervisor caches the token for five minutes minus 30 seconds.

  5. The supervisor injects the token. The supervisor writes the token into the request: Authorization: Bearer <token> by default, or the raw token in a custom header with auth_style: header. Injection replaces every agent-supplied instance of that header. The supervisor then forwards the request upstream. A failed grant returns HTTP 502, and the request is not forwarded. The access token is not placed in the sandbox environment.

Step 3 is where the full SPIFFE ID counts. Keycloak maps the sub to exactly one client: when more than one enabled client matches, the lookup fails. Keycloak documents that each client must have a unique SPIFFE ID per realm. Every sandbox SPIFFE ID therefore needs its own Keycloak client, and creating those clients is a requirement the operator must automate.

What the gateway checks

With client_credentials, the gateway is not on the token request path. The supervisor sends the JWT-SVID directly to token_endpoint. The gateway supplies the provider state and the token_grant_owner metadata, which names the policy endpoint that may grant a credential. The supervisor requires that endpoint to admit the request before it acquires a token.

The gateway sees a JWT-SVID only with the token_exchange grant type, where it brokers an intermediate token for the supervisor. That flow requires a Workload API socket on the gateway as well. The gateway accepts the request only from a sandbox principal and only when the requested provider is attached to that sandbox. It then verifies the supervisor’s JWT-SVID against its own:

  • The issuer equals the issuer of the gateway’s JWT-SVID.

  • The audience contains the JWT-SVID audience of the token grant.

  • The signature verifies against the JWT bundles from the gateway’s Workload API.

  • The trust domain equals the gateway’s trust domain.

The gateway does not check the path of the SPIFFE ID, and it does not compare the SPIFFE ID with the calling sandbox. A JWT-SVID with the same issuer and trust domain, the right audience, and a valid signature passes, whichever workload its path names. The gateway uses the verified sub as the audience of the intermediate token.

Trust model

A sandbox’s JWT-SVID carries one identity value: the SPIFFE ID in its sub claim. SPIRE issues the JWT-SVID only to a workload that matches a registration entry, and the entry binds it to one Pod by its Pod UID. The Pod UID is attested, but it is not part of the SPIFFE ID, and relying parties never see it. The sandbox segment of the SPIFFE ID comes from a Pod annotation that the Pod creator writes, and no relying party checks it. What a JWT-SVID proves about a sandbox therefore depends on how tightly the registration selects Pods and on who can create or patch Pods in the sandbox namespace. It also depends on who can create or change ClusterSPIFFEID resources, which are cluster-scoped and set the SPIFFE ID of every Pod they select. The relying parties in this guide are Keycloak and, with the token_exchange grant type, the OpenShell gateway. This page separates what binds the identity from what names it, states how unique each value is, and explains why sandbox namespaces must stay administrative. For the token flow itself, see How it works.

What SPIRE attests

The k8s workload attestor of the SPIRE agent generates Kubernetes selectors for each workload that calls the agent. It finds the workload’s Pod through the calling process’s cgroup membership and then asks the kubelet about that Pod. Its selectors include the namespace (k8s:ns), the ServiceAccount (k8s:sa), Pod labels (k8s:pod-label), the container name (k8s:container-name), the Pod name (k8s:pod-name), and the Pod UID (k8s:pod-uid). Pod annotations are not among them.

A registration entry decides which of these selectors must match. SPIRE Controller Manager renders one entry for each Pod that a ClusterSPIFFEID selects. Every such entry carries k8s:pod-uid:<pod-uid>, and its parent ID names the node the Pod runs on. The controller manager adds the selectors that the workloadSelectorTemplates field renders. The sandbox registration in this guide adds k8s:container-name:supervisor and a Pod-name selector rendered from the sandbox ID annotation: k8s:pod-name:os-supervisor-{{ index .PodMeta.Annotations "openshell.ai/sandbox-id" }}. The driver names the supervisor container supervisor and the supervisor Pod os-supervisor-<sandbox-id>. SPIRE therefore serves the entry only to a Pod whose actual name is os-supervisor- followed by its own annotation value. A Pod name must be unique within a namespace and cannot be updated. Because the registration covers only the sandbox namespace, at most one live Pod at a time can attest for a given sandbox ID. Another Pod can take the name os-supervisor-<sandbox-id> only while the real supervisor Pod does not exist, for example while the sandbox is stopped.

Kubernetes generates the Pod UID when it creates the Pod. The Kubernetes API describes the UID as unique in time and space, populated by the system, and read-only. The Pod creator does not choose it.

With this guide’s registration, attestation answers one question: does the caller run in the supervisor container of the Pod with this UID and name? The Pod UID binds the entry, but the SPIFFE ID does not contain it. A relying party sees the SPIFFE ID in the sub claim and nothing about the Pod.

What names the identity

The SPIFFE ID in an entry comes from the spiffeIDTemplate of the ClusterSPIFFEID. The template can read the trust domain, the Pod metadata, and the Pod spec, among other data. The podSelector and namespaceSelector fields choose the Pods by label.

Each segment of spiffe://<trust-domain>/openshell/sandbox/<sandbox-id> has a different source:

  • <trust-domain> is the trust domain the controller manager operates for, inserted by {{ .TrustDomain }}. Keycloak rejects a sub outside its configured trust domain, and with token_exchange the gateway requires the trust domain of its own JWT-SVID.

  • /openshell/sandbox/ is fixed text that the author of the ClusterSPIFFEID chose.

  • <sandbox-id> is the value of the Pod’s openshell.ai/sandbox-id annotation, which the Pod creator writes. No relying party checks it, but the Pod-name selector ties it to the name of the attested Pod.

The sandbox registration in this guide selects Pods in the sandbox namespace that carry the labels openshell.ai/managed-by: openshell, openshell.ai/component: supervisor, and openshell.ai/boundary-role: supervisor. The OpenShell gateway’s Kubernetes driver creates the supervisor Pod and writes these labels and the annotation.

The driver also writes the openshell.ai/sandbox-id annotation into the workload Pod template, with the sandbox’s own ID, after any annotations from the sandbox template. A sandbox creator can put other openshell.ai/ labels on the workload Pod through the sandbox template, because the gateway checks template labels and annotations only for count and size and the driver writes them unchanged into the workload Pod template. The driver overwrites openshell.ai/boundary-role with workload in that template and checks that value again on the admitted Pod. That label keeps the workload Pod out of the sandbox registration, and the container-name and Pod-name selectors require the supervisor’s container and Pod name on top. The driver also removes any spiffe-workload-api volume and mount from the workload Pod, and caller resource admission accepts only emptyDir, downwardAPI, persistentVolumeClaim, and the generation’s own Secret volumes.

Labels and annotations hold whatever the Pod creator wrote. The SPIRE agent reports labels as the creator set them and emits no selector for annotations.

Sandbox ID

The gateway generates the sandbox ID as a random UUID when it creates the sandbox. Each sandbox has one sandbox ID, and the driver writes it on every supervisor Pod of that sandbox. That makes the sandbox ID unique per sandbox only while the driver is the sole writer of the annotation on Pods that the registration selects.

Fallback identity

Zero Trust Workload Identity Manager creates a fallback ClusterSPIFFEID named zero-trust-workload-identity-manager-spire-default. Its template is spiffe://<trust-domain>/ns/<ns>/sa/<sa>, and it sets fallback: true. A fallback applies only when no other non-fallback ClusterSPIFFEID matches the Pod. Its namespace selector excludes the operator’s own namespace, and the controller manager ignores kube-system, kube-public, local-path-storage, and openshift-*. In all other namespaces, every Pod that no registration selects gets this ID, including the workload Pod of each sandbox.

The fallback ID depends only on the namespace and the ServiceAccount. The Kubernetes driver assigns one configured ServiceAccount to the workload and supervisor Pods of every sandbox, and in managed mode it creates that ServiceAccount in each workspace namespace. All workload Pods in a sandbox namespace share one fallback SPIFFE ID, and that ID names no sandbox.

One Keycloak client per SPIFFE ID

Keycloak finds the client for a client assertion by its sub, the SPIFFE ID. The lookup reads at most two enabled clients whose federated JWT credential subject matches. When it finds more than one, it fails with "Multiple clients matches attributes". Keycloak documents that each client must have a unique SPIFFE ID per realm. Each sandbox SPIFFE ID needs exactly one Keycloak client. Every Pod that holds a given SPIFFE ID authenticates as that same client, so a shared fallback ID cannot tell sandboxes apart at Keycloak.

What the relying parties check

With the client_credentials grant type, the gateway never sees the JWT-SVID. The supervisor sends it directly to the token endpoint. Keycloak checks that the sub lies in its configured trust domain, and its client lookup by sub is the only check on the full SPIFFE ID.

With token_exchange, the gateway verifies the supervisor’s JWT-SVID issuer, audience, signature, and trust domain against its own JWT-SVID. It does not check the SPIFFE ID path. In the final exchange, the supervisor sends its own JWT-SVID to the token endpoint as the client assertion, so Keycloak’s client lookup by sub applies as well.

No relying party compares the <sandbox-id> segment with the sandbox that runs in the attested Pod. That segment is only as trustworthy as the registration that selects the Pod and the access control that limits who creates or patches Pods in the sandbox namespace.

Why sandbox namespaces must stay administrative

The Kubernetes driver requires sandbox namespaces to stay administrative. Untrusted principals must not create permissive network policies, create Pods, read bootstrap Secrets, or spoof the OpenShell role labels there. In the shared and managed workspace modes, only the driver and its trusted Agent Sandbox controller may administer the sandbox namespace, the Sandbox resources, the sandbox Pods, or the configured sandbox ServiceAccount. In operator mode, the platform operator owns the namespace lifecycle and must keep other principals from creating or changing Sandbox resources, creating sandbox Pods with fabricated owner references, or using the configured sandbox ServiceAccount.

Two exposures remain with this guide’s registration:

  • Anyone with Kubernetes permission to create Pods in a sandbox namespace can set the supervisor labels, the container name, the Pod name, and any openshell.ai/sandbox-id value, and permission to patch Pods changes their labels and annotations. The controller manager then registers such a Pod under the named sandbox’s SPIFFE ID, and SPIRE attests it by its own Pod UID when its name is os-supervisor- followed by its annotation value. In the shared and managed workspace modes, only the driver and the Agent Sandbox controller may hold that permission; in operator mode, the platform operator must keep it from other principals.

  • The fallback ID spiffe://<trust-domain>/ns/<ns>/sa/<sa> covers the workload Pods of a sandbox namespace and names no sandbox. No Keycloak client or other relying party may accept it.

Before you begin

  • You have an OpenShift cluster at version 4.19 or later, with oc configured. OpenShell requires OpenShift 4.19 or later, and the Zero Trust Workload Identity Manager README lists the same minimum.

  • You have access to the cluster with cluster-admin privileges.

  • Your cluster can install operators from the redhat-operators catalog source in openshift-marketplace.

  • Your cluster has a default StorageClass. The SPIRE server, the OpenShell gateway, and every sandbox workspace use volume claims that name no storage class. Without a default StorageClass, the workspace claim stays Pending and the sandbox never starts.

  • OpenShell 0.1.4 runs on the cluster, installed with Helm as the OpenShell OpenShift guide describes. That guide also requires the Agent Sandbox controller and a network plugin that enforces ingress and egress NetworkPolicy in sandbox namespaces.

Install workload identity

SPIRE issues the JWT-SVIDs that sandbox supervisors present to the identity provider (IdP). On OpenShift, the Zero Trust Workload Identity Manager operator deploys and configures SPIRE. This page installs the operator, creates its five operand resources, and verifies the result. How it works shows where each component takes part in a token grant.

The commands and manifests on this page ran against operator version 1.1.2 from the stable-v1 channel.

Before you begin

  • You have access to the cluster with cluster-admin privileges.

  • The SPIRE server can claim a persistent volume of at least 1Gi.

  • Your cluster can install operators from the redhat-operators catalog source in openshift-marketplace.

Choose the trust domain and the JWT issuer

The trust domain is the authority part of every SPIFFE ID, spiffe://<trust-domain>/<path>, and the cluster name identifies this cluster inside the trust domain. Both are fields of the ZeroTrustWorkloadIdentityManager resource, and neither can change after you create it.

The operator derives Route hosts from these values. The Route of the OIDC discovery provider uses the host part of jwtIssuer, and a federation Route, when configured, uses federation.<trust-domain>. Red Hat recommends the cluster’s apps domain as the trust domain. This page uses the apps domain as the trust domain and https://oidc-discovery.<apps-domain>; as the JWT issuer. The default ingress controller serves *.<apps-domain>, which includes the issuer host.

  1. Read the apps domain of your cluster.

    Check: the command prints one DNS name, which is <apps-domain> in the rest of this page.

    oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}'

  2. Choose <cluster-name>. It must be a DNS subdomain name of at most 63 characters: lowercase letters, digits, hyphens, and dots, starting and ending with a letter or digit.

Create the operands

The operator manages SPIRE through five cluster-scoped resources. Each one is a singleton, and its name must be cluster. Red Hat documents this creation order: ZeroTrustWorkloadIdentityManager, SpireServer, SpireAgent, SpiffeCSIDriver, SpireOIDCDiscoveryProvider.

  1. Create the ZeroTrustWorkloadIdentityManager resource with your trust domain and cluster name.

    oc apply -f - <<'EOF'
apiVersion: operator.openshift.io/v1alpha1
kind: ZeroTrustWorkloadIdentityManager
metadata:
  name: cluster
spec:
  trustDomain: <apps-domain>
  clusterName: <cluster-name>
  bundleConfigMap: spire-bundle
EOF

    bundleConfigMap names the ConfigMap in which the operator keeps the trust bundle. spire-bundle is its default, and the field is immutable.

  2. Create the SpireServer resource.

    oc apply -f - <<'EOF'
apiVersion: operator.openshift.io/v1alpha1
kind: SpireServer
metadata:
  name: cluster
spec:
  jwtIssuer: https://oidc-discovery.<apps-domain>
  caKeyType: rsa-2048
  defaultJWTValidity: 5m
  caSubject:
    commonName: SPIRE Server CA
    organization: <cluster-name>
    country: US
  persistence:
    size: 1Gi
    accessMode: ReadWriteOnce
  datastore:
    databaseType: sqlite3
    connectionString: /run/spire/data/datastore.sqlite3
EOF

    jwtIssuer must match the issuer of the OIDC discovery provider in a later step. caKeyType sets the key type of the server CA for both X.509 and JWT; rsa-2048 is the default. defaultJWTValidity is the lifetime of a JWT-SVID whose registration entry sets none; 5m is also the default. caSubject.country takes a two-letter ISO 3166-1 code. persistence cannot change after creation. Without persistence.storageClass, the operator sets no storage class on the SPIRE server’s volume claim. The datastore values are the defaults: an SQLite file in the server’s data volume at /run/spire/data.

    Leave federation unset. The SpireServer resource rejects an update that removes federation once it is set. Keycloak accepts an OpenID Connect JWKS endpoint as its SPIFFE bundle endpoint, and this guide points it at the /keys endpoint of the OIDC discovery provider, so the guide needs no federation.

  3. Create the SpireAgent resource with explicit attestors.

    oc apply -f - <<'EOF'
apiVersion: operator.openshift.io/v1alpha1
kind: SpireAgent
metadata:
  name: cluster
spec:
  nodeAttestor:
    k8sPSATEnabled: "true"
  workloadAttestors:
    k8sEnabled: "true"
    workloadAttestorsVerification:
      type: auto
EOF

    The operator adds a node attestor plugin only when nodeAttestor is present with k8sPSATEnabled: "true", and a workload attestor plugin only when workloadAttestors is present with k8sEnabled: "true". Without these fields, the operator configures no attestor plugins. k8sPSATEnabled selects the k8s_psat node attestor, configured with the cluster name. k8sEnabled selects the Kubernetes workload attestor, which finds the calling Pod through the kubelet. workloadAttestorsVerification.type: auto makes the agent verify the kubelet certificate against /etc/kubernetes/kubelet-ca.crt. Without workloadAttestorsVerification, the operator configures the agent to skip kubelet certificate verification.

  4. Create the SpiffeCSIDriver resource.

    oc apply -f - <<'EOF'
apiVersion: operator.openshift.io/v1alpha1
kind: SpiffeCSIDriver
metadata:
  name: cluster
spec: {}
EOF

    The defaults name the CSI driver csi.spiffe.io and share the agent socket directory /run/spire/agent-sockets with the SPIRE agent. The driver mounts that directory into Pods that request a csi.spiffe.io volume. The Workload API socket file in it is spire-agent.sock.

  5. Create the SpireOIDCDiscoveryProvider resource with the same issuer as the SpireServer.

    oc apply -f - <<'EOF'
apiVersion: operator.openshift.io/v1alpha1
kind: SpireOIDCDiscoveryProvider
metadata:
  name: cluster
spec:
  jwtIssuer: https://oidc-discovery.<apps-domain>
EOF

    With the default managedRoute: "true", the operator creates the Route spire-oidc-discovery-provider with the issuer host, re-encrypt TLS termination, and a redirect from HTTP.

The operator sets the tolerations of the SPIRE agent and SPIFFE CSI driver DaemonSets from spec.tolerations of their resources. The scheduler does not place their Pods on a node with a NoSchedule taint they do not tolerate. The CSI driver registers csi.spiffe.io with the kubelet of each node it runs on. When the SPIFFE socket is configured, OpenShell supervisor Pods mount a csi.spiffe.io volume, which needs the driver registered with the kubelet of their node. When sandboxes run on tainted nodes, add a matching toleration to spec.tolerations of both SpireAgent and SpiffeCSIDriver:

spec:
  tolerations:
  - key: <taint-key>
    operator: Exists
    effect: NoSchedule

The operator sets the ZeroTrustWorkloadIdentityManager resource as owner of the other four resources. Deleting the ZeroTrustWorkloadIdentityManager resource deletes the operands and their resources.

Configure OpenShell

OpenShell needs an implementation of the SPIFFE Workload API, served to Pods through the csi.spiffe.io CSI driver. Sandbox supervisors use it for token grants, and the gateway uses it for token exchange. This guide uses Zero Trust Workload Identity Manager, set up in Install workload identity. This page enables the Workload API socket in the OpenShell Helm chart and checks where it appears.

How OpenShell uses the socket

OpenShell mounts the Workload API socket only when the Kubernetes driver setting provider_spiffe_workload_api_socket_path holds a path. In the Helm chart, the setting belongs to the openshell.drivers.kubernetes table of gatewayConfig, which the chart renders into gateway.toml. An empty or omitted path disables the socket. The chart also accepts server.providerTokenGrants.spiffe as a deprecated alias for this setting. When your values set both, gatewayConfig wins. With the path set, the setting affects three Pods:

Gateway Pod

The chart adds a read-only csi.spiffe.io volume, mounts it at the parent directory of the socket path, and sets OPENSHELL_GATEWAY_SPIFFE_WORKLOAD_API_SOCKET. The gateway reads this socket only for token exchange. It fetches its own JWT-SVID there and verifies supervisor JWT-SVIDs with the JWT bundles from the Workload API. client_credentials grants do not use the gateway socket, but the chart mounts it whenever the socket path is set.

Supervisor Pod

When the driver creates a supervisor Pod, it mounts a read-only csi.spiffe.io volume into the supervisor container at the parent directory of the socket path and sets OPENSHELL_PROVIDER_SPIFFE_WORKLOAD_API_SOCKET. The supervisor fetches its JWT-SVID for a token grant from this socket.

Workload Pod

The workload Pod, which runs the agent, receives no provider identity socket.

Supervisors authenticate to the gateway with sandbox JWTs that the gateway mints, not with SPIFFE. How it works shows the full token grant flow.

Before you begin

  • Zero Trust Workload Identity Manager runs with the SPIRE agent and the SPIFFE CSI driver, as described in Install workload identity.

  • OpenShell 0.1.4 runs on the cluster as the Helm release openshell in <namespace>. The OpenShell OpenShift guide describes this installation.

  • Sandboxes run in <namespace>, the chart default.

  • The gateway runs as the StatefulSet openshell, the chart default, so its Pod is openshell-0.

The CSI driver serves the socket directory of the SPIRE agent, and the socket file in it is spire-agent.sock. Register sandbox identities

SPIRE issues a JWT-SVID only to a workload that matches a registration, and the registration alone decides which sandbox that identity names. This page creates the ClusterSPIFFEID that gives each sandbox supervisor the SPIFFE ID spiffe://<trust-domain>/openshell/sandbox/<sandbox-id> and checks the SPIRE entry it produces. Trust model explains in full what attestation proves and what it leaves open.

Before you trust a sandbox identity, know which parts of it SPIRE attests and how unique each part is. With this registration, SPIRE attests the caller’s Pod UID, container name, and Pod name. The <sandbox-id> segment of the SPIFFE ID comes from a Pod annotation that the Pod creator writes, and no relying party checks it. The registration on this page ties that segment to the attested Pod name, which is unique within the namespace.

How the registration selects supervisors

The registration has five parts, and each one narrows the set of Pods that can hold a sandbox SPIFFE ID.

className

Zero Trust Workload Identity Manager configures SPIRE Controller Manager with the class name zero-trust-workload-identity-manager-spire and does not watch resources without a class name. The controller manager ignores a ClusterSPIFFEID that lacks this class name.

spiffeIDTemplate

The template renders the SPIFFE ID from the trust domain and the Pod’s openshell.ai/sandbox-id annotation. The driver writes that annotation on the supervisor Pod with the sandbox ID.

namespaceSelector

The selector matches the sandbox namespace by its kubernetes.io/metadata.name label, which Kubernetes sets on every namespace. With one namespace, a Pod name identifies at most one Pod among all Pods the registration selects.

podSelector

The selector matches the labels openshell.ai/managed-by: openshell, openshell.ai/component: supervisor, and openshell.ai/boundary-role: supervisor, which the driver sets on the supervisor Pod.

workloadSelectorTemplates

The templates add k8s:container-name:supervisor and k8s:pod-name:os-supervisor-<annotation value> to the entry. The controller manager always adds k8s:pod-uid:<pod-uid> as well. The driver names the supervisor container supervisor and the supervisor Pod os-supervisor-<sandbox-id>. The SPIRE agent emits k8s:container-name because SpireAgent leaves workloadAttestors.disableContainerSelectors at its default "false".

Labels alone do not identify a supervisor. A sandbox creator can put openshell.ai/ labels on the workload Pod through the sandbox template, because the gateway checks template labels only for count and size. The driver writes them unchanged into the workload Pod template of the Sandbox resource. The driver overwrites openshell.ai/boundary-role with workload in that template and checks the value again on the admitted Pod. boundary-role: supervisor is therefore the one selected label that the sandbox template cannot place on a workload Pod.

The workload selectors close the remaining gap. The SPIRE agent serves an entry only when all of the entry’s selectors are among the selectors it attested for the caller. A Pod that matches the labels by mistake still gets no SVID unless it runs a container named supervisor and its name is os-supervisor- followed by its own annotation value.

Of the two Pods of a sandbox, only the supervisor Pod receives the Workload API socket. The driver mounts the csi.spiffe.io volume into the supervisor container and removes any spiffe-workload-api volume and mount from the workload Pod. Caller resource admission accepts only emptyDir, downwardAPI, persistentVolumeClaim, and the generation’s own Secret volumes.

The OpenShell repository contains deploy/helm/openshell/ci/values-spire-stack.yaml, whose header describes it as values for the local Helm dev environment. It is a development overlay, not a pattern to copy. Its ClusterSPIFFEID renders the SPIFFE ID from the annotation and its podSelector matches only the label openshell.ai/managed-by: openshell, a label that a sandbox creator can put on a workload Pod. It has no boundary-role label and no workload selector templates.

Keep the sandbox namespace administrative. The registration holds only while untrusted principals cannot create or patch Pods there.

  • Anyone with permission to create Pods in the sandbox namespace can create a Pod with the supervisor labels, a container named supervisor, any openshell.ai/sandbox-id annotation, and the name os-supervisor-<sandbox-id>. SPIRE then attests that Pod for the named sandbox’s SPIFFE ID whenever the real supervisor Pod does not exist. In the shared and managed workspace modes, only the driver and its trusted Agent Sandbox controller may administer the sandbox namespace and its Pods. In operator mode, the platform operator must keep other principals from creating sandbox Pods or changing Sandbox resources.

  • In all namespaces except the operator namespace and the namespaces the controller manager ignores, Pods that no registration selects, including workload Pods, get the fallback ID spiffe://<trust-domain>/ns/<namespace>/sa/<service-account> from Zero Trust Workload Identity Manager. That ID names no sandbox, and no Keycloak client or other relying party may accept it.

Configure Keycloak

Keycloak accepts a sandbox’s JWT-SVID only when it trusts the SPIRE signing keys and maps the SPIFFE ID in the SVID to exactly one client. This page creates a realm with a SPIFFE identity provider for the signing keys and describes the client that each sandbox needs. How it works shows where these checks happen in a token grant.

This setup is only known to work with Keycloak. Red Hat build of Keycloak is the only token service it was verified with.
How Keycloak accepts a JWT-SVID

The supervisor sends its JWT-SVID as the client assertion of a client_credentials request, without a client ID. Keycloak handles the request in three steps.

  1. Find the client. For the assertion type urn:ietf:params:oauth:client-assertion-type:jwt-spiffe, Keycloak looks up the enabled client whose attribute jwt.credential.sub equals the sub claim, the sandbox SPIFFE ID. If more than one enabled client matches, the lookup fails.

  2. Find the identity provider. The client’s attribute jwt.credential.issuer holds the alias of the SPIFFE identity provider that verifies the assertion. Keycloak verifies the assertion only for a client whose authenticator type is federated-jwt.

  3. Verify the JWT-SVID. The identity provider rejects a sub outside its trust domain. It fetches the signing keys with an HTTP GET on its bundle endpoint. It accepts exactly one audience, the realm issuer https://<keycloak-host>/realms/<realm>;.

The client_credentials grant also requires a confidential client with service accounts enabled. Keycloak issues the token for the client’s service account user, whose name is service-account- followed by the client ID.

Before you begin

  • Keycloak runs as described in Install Keycloak, with the Keycloak resource keycloak in the namespace keycloak and the host name <keycloak-host>.

  • The SPIRE OIDC discovery provider serves https://oidc-discovery.<apps-domain>; as described in Install workload identity. <trust-domain> is the trust domain configured there.

  • Sandbox supervisors receive the SPIFFE ID spiffe://<trust-domain>/openshell/sandbox/<sandbox-id> as described in Register sandbox identities.

  • You choose <realm>, the name of the realm, for example openshell.

Create the realm and the SPIFFE identity provider

A KeycloakRealmImport resource creates a realm from a realm representation. The realm on this page holds one SPIFFE identity provider, which trusts JWT-SVIDs from the trust domain and reads their signing keys from the SPIRE OIDC discovery provider.

  1. Create the KeycloakRealmImport.

    oc apply -f - <<'EOF'
apiVersion: k8s.keycloak.org/v2beta1
kind: KeycloakRealmImport
metadata:
  name: openshell-realm
  namespace: keycloak
spec:
  keycloakCRName: keycloak
  realm:
    realm: <realm>
    enabled: true
    identityProviders:
      - alias: spiffe
        providerId: spiffe
        enabled: true
        config:
          trustDomain: spiffe://<trust-domain>
          bundleEndpoint: https://oidc-discovery.<apps-domain>/keys
EOF

    keycloakCRName names the Keycloak resource, which must be in the same namespace. realm takes a realm representation. providerId: spiffe selects the SPIFFE identity provider. alias is the name that each client references in its jwt.credential.issuer attribute. trustDomain is the trust domain with the spiffe:// prefix and no trailing slash, because Keycloak accepts only a sub that starts with this value followed by /. Keycloak also rejects a trust domain that is not spiffe:// followed only by lowercase letters, digits, dots, hyphens, and underscores, so a trailing slash fails validation. bundleEndpoint is the HTTPS URL of a SPIFFE bundle endpoint or of an OpenID Connect JWKS endpoint. This page uses the /keys endpoint of the SPIRE OIDC discovery provider, which serves the JSON Web Key Set for JWT validation.

    Keycloak must trust the certificate that the bundle endpoint presents. Its truststore holds the Java default truststore, the Kubernetes service account CA and the OpenShift service CA when they are mounted, and the certificates added through spec.truststores of the Keycloak resource. If no CA in that truststore issued the bundle endpoint’s certificate, add the issuing CA through spec.truststores.

  2. Wait for the import.

    Check: the condition Done is True and the condition HasErrors is False.

    oc get keycloakrealmimport openshell-realm -n keycloak -o jsonpath='{range .status.conditions[*]}{.type}={.status}{" "}{end}'

  3. Check the realm discovery document.

    Check: the token_endpoint is https://<keycloak-host>/realms/<realm>/protocol/openid-connect/token.

    curl -sS "https://<keycloak-host>/realms/<realm>/.well-known/openid-configuration"

The import only creates realms. It does not overwrite an existing realm with the same name, and it does not update or delete a realm. The operator documentation recommends deleting the KeycloakRealmImport after the import, which removes its Job and Pod. Delete it only after both checks pass. The import status check then finds no resource, and the discovery document check remains the durable check of the realm. Only namespace administrators should be able to create or edit KeycloakRealmImport resources.
Create a client for each sandbox

Keycloak maps each SPIFFE ID to one client, and each sandbox has its own SPIFFE ID. A sandbox gets no token until its client exists.

Every sandbox needs its own client in the realm, with its SPIFFE ID in jwt.credential.sub. You must automate creating that client for each new sandbox. Keycloak documents that each client must have a unique SPIFFE ID per realm.

Create the client through the Admin REST API or the Admin Console with the following client representation. Replace <sandbox-id> with the ID of the sandbox.

{
  "clientId": "sandbox-<sandbox-id>",
  "publicClient": false,
  "serviceAccountsEnabled": true,
  "standardFlowEnabled": false,
  "directAccessGrantsEnabled": false,
  "clientAuthenticatorType": "federated-jwt",
  "attributes": {
    "jwt.credential.issuer": "spiffe",
    "jwt.credential.sub": "spiffe://<trust-domain>/openshell/sandbox/<sandbox-id>"
  }
}

clientId is a name you choose, and Keycloak names the service account user service-account-sandbox-<sandbox-id> after it. publicClient: false and serviceAccountsEnabled: true let the client use the client_credentials grant. standardFlowEnabled: false and directAccessGrantsEnabled: false turn off the Authorization Code Flow and Direct Access Grants. clientAuthenticatorType: federated-jwt authenticates the client with an assertion that an identity provider verifies. jwt.credential.issuer is the alias of the SPIFFE identity provider. jwt.credential.sub is the sandbox SPIFFE ID.

Values for the provider profile

A provider profile that obtains tokens from this realm uses these token grant values.

token_endpoint

https://<keycloak-host>/realms/<realm>/protocol/openid-connect/token.

client_assertion_type

urn:ietf:params:oauth:client-assertion-type:jwt-spiffe. OpenShell defaults to urn:ietf:params:oauth:client-assertion-type:jwt-bearer, so the profile must set this value.

jwt_svid_audience

Can stay unset. For a token endpoint with /realms/<realm> in its path, the supervisor derives the audience https://<keycloak-host>/realms/<realm>;, which has the same form as the realm issuer.

Protect the target API

For a request to a matching endpoint, the supervisor obtains an access token from Keycloak and injects it before it forwards the request upstream. The profiles in this guide set auth_style: bearer with header_name: Authorization, so the token goes into the Authorization header as Bearer <token> and replaces every Authorization header the agent sent. The token is not placed in the sandbox environment. OpenShell rejects token values that are unsafe for an HTTP header but does not validate the token for the target; the API that receives it decides whether the token grants access. That API must validate the token and restrict access by the identity the token asserts. This page lists what to validate and which identity to authorize on. How it works shows where the token comes from.

Validate the access token

Keycloak access tokens are JSON Web Tokens (JWT), signed with JSON Web Signature (JWS). The API validates each token in one of two ways.

Local validation

The API verifies the signature with the realm’s public keys. The certificate endpoint https://<keycloak-host>/realms/<realm>/protocol/openid-connect/certs returns the keys that the realm has enabled, as JSON Web Keys. The API picks the key by the Key ID (kid) in the JWS header and can cache the keys.

Introspection

The API sends the token to https://<keycloak-host>/realms/<realm>/protocol/openid-connect/token/introspect, which returns the active state of the token. Only confidential clients can call this endpoint, so the API needs its own client in the realm. Keycloak allows introspection only when that client is in the token’s audience (aud), unless the client enables Allow token introspection without audience check. Each validation is a network call to Keycloak.

With local validation, the API also checks these claims:

  • iss exactly matches the realm issuer, https://<keycloak-host>/realms/<realm>;.

  • The current time is before exp.

  • The JWS header alg is not none.

  • aud contains the identifier that the API expects for itself.

Put the API in the audience

This section is outside the verified path of this guide.

Keycloak does not add the client that a token was issued for to the access token audience. The Audience Resolve mapper in the default client scope roles adds the client ID of each client that has a client role in the token. A sandbox token carries the API’s identifier only when you configure it.

The Audience mapper adds a fixed audience: the client ID of a client you select, or a custom value such as a URL. Add the Audience mapper to a client scope and link that scope to each sandbox client as a default client scope, for example when the client is created. The mappers of a default client scope apply to every token issued for the client. A realm default client scope of type Default is linked to every client created after the change, sandbox client or not. It is not linked to existing clients, so existing sandbox clients need the scope linked explicitly. If the API uses introspection, the audience must be the client ID of the API’s own client.

Authorize on the sandbox’s client

A token that passes these checks proves that Keycloak issued it in this realm. Tokens for every client in the realm carry the same issuer and verify against the same realm keys. That includes the client of every other sandbox and, with token_exchange, the gateway client; token_exchange is outside the verified path of this guide. Authorize each request on the azp claim, the client that the token was issued for, not on the realm alone.

Each sandbox has its own client, and Keycloak resolves a JWT-SVID to the one enabled client whose jwt.credential.sub is the sandbox SPIFFE ID. Configure Keycloak names that client sandbox-<sandbox-id>. Keycloak always sets azp to the client ID that the token was issued for, so a token issued to that client carries azp sandbox-<sandbox-id>.

A token can also carry a client_id claim with the same client ID. The Client ID mapper of the client scope service_account writes it. Keycloak links that scope as a default client scope when service accounts are enabled through the Admin REST API or the Admin Console. Treat client_id only as an equivalent of azp where it is present.

Map the azp values that may call the API to the operations each one may perform, and reject every other value.

Create the provider

A provider profile tells the supervisor where to obtain a token and which requests receive it. You attach a provider created from the profile to the sandbox.

  1. Write the provider profile to a file.

    cat > keycloak-token-grant-profile.yaml <<'EOF'
id: keycloak-token-grant
display_name: Keycloak SPIFFE token grant
category: other
credentials:
  - name: access_token
    required: false
    auth_style: bearer
    header_name: Authorization
    token_grant:
      token_endpoint: https://<keycloak-host>/realms/openshell/protocol/openid-connect/token
      client_assertion_type: urn:ietf:params:oauth:client-assertion-type:jwt-spiffe
      scopes: [openid]
endpoints:
  - host: keycloak-service.keycloak.svc.cluster.local
    port: 8080
    protocol: rest
    access: read-only
    enforcement: enforce
binaries:
  - /usr/bin/curl
  - /usr/local/bin/curl
EOF

    id is the value that openshell provider create --type takes. category is informational. required: false makes the credential optional, so the provider needs no stored value for it. auth_style: bearer with header_name: Authorization injects the token as Authorization: Bearer <token>. token_grant holds the values from Values for the provider profile, with jwt_svid_audience unset. scopes: [openid] requests the openid scope, because the userinfo endpoint rejects a token without it. endpoints names the Keycloak Service inside the cluster, and the supervisor injects the token only into requests to this endpoint. protocol: rest turns on request inspection. access: read-only allows GET, HEAD, and OPTIONS, and enforcement: enforce blocks requests that break these rules. binaries lists the executables that may reach the endpoint.

  2. Lint the profile before you import it. Lint asks the gateway to check the profile without storing it. It reports an error when the workspace already holds a profile with this id.

    openshell profile lint -f keycloak-token-grant-profile.yaml

  3. Import the profile into the current workspace.

    openshell profile import -f keycloak-token-grant-profile.yaml

  4. Create the provider. Create providers for token-grant-only profiles with --runtime-credentials, as the OpenShell documentation instructs. The flag records the provider without stored credentials and makes explicit that the credential is resolved at runtime.

    openshell provider create --name keycloak-token-grant --type keycloak-token-grant --runtime-credentials

  5. Check the provider.

    Check: the provider keycloak-token-grant has the type keycloak-token-grant.

    openshell provider get keycloak-token-grant
Create the sandbox

The sandbox runs curl, so its image must contain curl. This page uses the community base image ghcr.io/nvidia/openshell-community/sandboxes/base:latest. OpenShell uses a policy that ships in an image only when the sandbox has no policy of its own, and a sandbox with an invalid image policy does not start. The command on this page passes its own policy with --policy.

  1. Write the sandbox policy to a file.

    cat > sandbox-policy.yaml <<'EOF'
version: 1

filesystem_policy:
  include_workdir: true
  read_only:
    - /usr
    - /lib
    - /proc
    - /dev/urandom
    - /app
    - /etc
    - /var/log
  read_write:
    - /sandbox
    - /tmp
    - /dev/null

landlock:
  compatibility: best_effort

process:
  run_as_user: sandbox
  run_as_group: sandbox
EOF

    The policy sets only filesystem, Landlock, and process settings. include_workdir, read_only, and read_write set the paths the workload can read and write, and process names the user and group of the workload. With compatibility: best_effort, the sandbox runs without the filesystem rules and logs a high-severity finding when none of the listed paths can be applied or Landlock fails to enforce the rules. User guide

User overview

Your agent runs in an OpenShell sandbox, an isolated boundary around the agent’s processes. It needs to call your API, and your API expects an access token. OpenShell usually gives an agent that kind of access through a provider, which connects a service name to a stored credential. The supervisor, which runs on the trusted side of the sandbox boundary and checks each request against policy, hands that credential out only where policy allows it. With the client_credentials grant that this guide uses, a token grant replaces the stored credential with a short-lived access token. When your agent calls your API, the supervisor adds an access token to the request on the way out. When it has no cached token, it first proves the sandbox’s identity to an OAuth2 token service and receives a new one. The provider stores no credential, and the token isn’t placed in the sandbox environment. In this section you set up such a provider for your API, attach it to a sandbox, and check that your API receives the token.

What you work with

OpenShell is a runtime for autonomous AI agents. It lets agents read files, call APIs, and use credentials, while a policy you declare limits what each agent can touch. Each agent runs in a sandbox, an isolated boundary that owns the agent’s processes and forwards its network traffic to the supervisor. The supervisor sits on the trusted side of that boundary: it checks requests against policy, supplies credentials, and opens approved connections. A provider profile describes the credentials, endpoints, and binaries of a provider type. For a token grant, it says where the supervisor gets the token, which requests receive it, and which programs may send them.

The sandbox’s identity comes from SPIFFE, a standard for issuing identity to services across heterogeneous environments. A SPIFFE ID is a URI of the form spiffe://<trust-domain>/<path>: the trust domain names the system that issued the identity, and the path names the workload. The identity document that SPIFFE defines is the SVID (SPIFFE Verifiable Identity Document). A JWT-SVID is a signed JWT whose sub claim is the SPIFFE ID of the workload it was issued to. SPIRE, which your administrator runs, attests running software and issues SPIFFE IDs and SVIDs to it. The supervisor sends its JWT-SVID to the token service in place of a client secret.

Keycloak is open source identity and access management that adds authentication to applications and secures services. This guide uses the Red Hat build of Keycloak as the OAuth2 token service, the identity provider (IdP) that issues the access tokens. Its SPIFFE identity provider authenticates clients with SPIFFE JWT-SVIDs. The registration that your administrator creates gives each sandbox the SPIFFE ID spiffe://<trust-domain>/openshell/sandbox/<sandbox-id>, where <sandbox-id> is the ID of the sandbox. Keycloak looks up the one client whose SPIFFE ID matches the sub claim of the JWT-SVID, so every sandbox needs its own Keycloak client. Your administrator registers that client, so you tell them the ID of your sandbox.

The SPIFFE identity provider is a preview feature of Keycloak and is not fully supported. Preview features are disabled by default, are not recommended for production, and may change or be removed in a future release.

Get short-lived tokens for your API

Your agent needs to call your API, and your API wants a bearer token. You could put a secret into the sandbox, but you don’t have to. A provider with a token grant lets the sandbox supervisor fetch a short-lived token from Keycloak when the agent calls your API. The supervisor proves the sandbox’s identity with a SPIFFE JWT-SVID, so the provider stores no credential at all. It adds the token to the request on the way out, and the token never lands in the agent’s environment.

On this page you write a provider profile for your API, turn it into a provider, and attach the provider to a new sandbox. Then you send one request and check that the token arrived.

Before you begin

  • Your administrator has set up the platform as described in the Administrator guide.

  • You know the Keycloak host and the realm that your administrator uses. This page calls them <keycloak-host> and <realm>.

  • Your API accepts access tokens from that realm. Protect the target API describes what the API checks.

  • The openshell CLI operates on your active gateway. Add -g <gateway> to a command to select another gateway.

Write the provider profile

A provider profile answers three questions. Where does the supervisor get the token, which requests receive it, and which programs may send those requests?

  1. Write the profile to a file, and replace the placeholders with your own values.

    cat > api-token-profile.yaml <<'EOF'
id: <profile-id>
display_name: Token grant for my API
category: other
credentials:
  - name: access_token
    required: false
    auth_style: bearer
    header_name: Authorization
    token_grant:
      token_endpoint: https://<keycloak-host>/realms/<realm>/protocol/openid-connect/token
      client_assertion_type: urn:ietf:params:oauth:client-assertion-type:jwt-spiffe
      scopes: [<scope>]
endpoints:
  - host: <api-host>
    port: <api-port>
    protocol: rest
    access: read-only
    enforcement: enforce
binaries:
  - /usr/bin/curl
  - <client-binary>
EOF

Let’s walk through the fields.

id

The profile ID, in lowercase kebab-case with a-z, 0-9, and -. It is also the provider type, the value of --type when you create the provider.

category

Informational only.

required: false

Makes the credential optional, so the provider needs no stored value.

auth_style: bearer with header_name: Authorization

Injects the token as Authorization: Bearer <token>. It replaces any Authorization header that the agent sent.

token_endpoint

The token endpoint of your realm.

client_assertion_type

The SPIFFE assertion type that Keycloak expects.

scopes

The scopes your API expects. The supervisor sends them as one space-separated scope parameter.

jwt_svid_audience

Stays unset. For a token endpoint with /realms/<realm> in its path, the supervisor derives the audience https://<keycloak-host>/realms/<realm>;.

endpoints

The host and port of your API, as the agent calls it. The supervisor injects the token only into requests to these endpoints. protocol: rest turns on request inspection. access picks a preset. read-only allows GET, HEAD, and OPTIONS, read-write adds POST, PUT, and PATCH, and full allows all methods and paths. enforcement: enforce blocks requests that break these rules.

binaries

The executables that may reach your API. /usr/bin/curl is there for the test request at the end of this page. If your image has curl at another path, use that path. <client-binary> is the executable that opens the connection to your API. That’s not always the command you run. A Python or Node.js script runs as its interpreter, so list the interpreter, such as /usr/bin/python3.12. List the real path, not a symlink, and find it with readlink -f inside the sandbox. A listed binary also covers the processes it starts.

Keep client_assertion_type set to urn:ietf:params:oauth:client-assertion-type:jwt-spiffe. OpenShell defaults to urn:ietf:params:oauth:client-assertion-type:jwt-bearer, and the Keycloak SPIFFE identity provider accepts only the jwt-spiffe type. With the default, your sandbox gets no token.

You’ll notice that the endpoint has no tls field. Leave it out. OpenShell then terminates TLS itself, and that’s how it can inspect the request and add the header. The only value the field accepts is skip, and a profile with a token grant rejects skip because it bypasses the header injection.

The agent calls your API with its normal URL. The proxy detects TLS on each tunnel and terminates it with a CA that OpenShell generates for the sandbox. So with an https:// URL, the agent’s client must trust that sandbox CA. OpenShell provides it to the agent’s processes through the variables NODE_EXTRA_CA_CERTS, DENO_CERT, SSL_CERT_FILE, REQUESTS_CA_BUNDLE, CURL_CA_BUNDLE, and GIT_SSL_CAINFO. HTTPS to your API is outside the verified path of this guide, which tested the flow only with plain HTTP to an in-cluster Service.

Create the provider

Now you hand the profile to the gateway and create a provider from it.

  1. Lint the profile. Lint asks the gateway to check the profile without storing it. It also reports an error when your workspace already holds a profile with this id, so run it before you import.

    openshell profile lint -f api-token-profile.yaml

  2. Import the profile into your current workspace.

    openshell profile import -f api-token-profile.yaml

  3. Create the provider with --runtime-credentials, as OpenShell recommends for profiles whose only credentials come from token grants. The flag records the provider without stored credentials and makes explicit that the credential is resolved at runtime.

    openshell provider create --name "<provider-name>" --type "<profile-id>" --runtime-credentials

  4. Look at the provider.

    Check: the output shows the name <provider-name> and the type <profile-id>.

    openshell provider get "<provider-name>"
Create the sandbox

The sandbox runs your agent’s client, so its image has to contain that client.

The image must contain the programs that send the requests, at the paths the profile lists. A profile whose binaries don’t match the image still shows up in the catalog, but its token isn’t injected and its traffic is denied.

OpenShell uses a policy that ships in the image at /etc/openshell/policy.yaml only when the sandbox has no policy of its own. If that image policy is invalid, the sandbox doesn’t start, and OpenShell doesn’t fall back to the default policy. Passing your own policy with --policy avoids the image policy.

  1. Create the sandbox with the provider attached. <image> is your sandbox image, and <policy-file> is your sandbox policy. Verify the setup end to end shows a minimal policy. Your policy needs no network rule for your API, because the attached provider adds that rule to the sandbox’s effective policy. --detach keeps the CLI from attaching to the sandbox’s main process.

    openshell sandbox create --name "<sandbox-name>" --provider "<provider-name>" --from "<image>" --policy "<policy-file>" --detach

  2. Wait until the sandbox is ready, and note its ID. Repeat the command until the phase is Ready. The Id line shows the sandbox ID, a UUID.

    Check: the phase is Ready, and the Id line shows a UUID.

    openshell sandbox get "<sandbox-name>"

Every sandbox needs its own client in the Keycloak realm. Ask your administrator to register the Keycloak client for your sandbox, and give them the sandbox ID. Configure Keycloak describes that client. Until the client exists, Keycloak rejects the sandbox’s assertion, and the supervisor answers your agent’s requests with HTTP 502 without forwarding them.
Send a request

Let’s try it. The request leaves the agent without a credential, and the supervisor adds the token before it forwards the request to your API.

  1. Call your API from inside the sandbox. <api-url> is the URL of a GET endpoint of your API on <api-host> and <api-port>. -i prints the status line, so you can see the result.

    Check: your API answers with an HTTP status in the 200 range.

    openshell sandbox exec --name "<sandbox-name>" --no-tty -- curl -sS -i "<api-url>"

    A failed token grant shows up as HTTP 502. If you see one, ask your administrator to look for the cause, for example a missing client for your sandbox.

  2. Look at the agent’s environment.

    Check: the environment holds no access token.

    openshell sandbox exec --name "<sandbox-name>" --no-tty -- env

Your agent reached your API with a fresh token, and it never held a secret. For the whole chain with a worked example, see Verify the setup end to end.

Known limitations

This page lists what the verified path of this guide covers, what it leaves unverified, and what you must build yourself. Trust model explains what the sandbox identity proves.

Baseline

This guide was verified against openshell 5a7728c, spire 2f7861a, spiffe f97c46d, spire-controller-manager d24609e, ztwim a5ad11e, keycloak 3db007a (captured 2026-10-15). Later revisions of these sources may rename targets or change defaults.

Verified

The verified path of this guide is the client_credentials grant type with Red Hat build of Keycloak on OpenShift. It ran end to end with OpenShell 0.1.4, Zero Trust Workload Identity Manager 1.1.2, and Red Hat build of Keycloak 26.6.7. In that run, a sandbox supervisor obtained a JWT-SVID from SPIRE, presented it to Keycloak for an access token, and injected the token into a request to an API inside the cluster. Verify the setup end to end repeats that request.

Not verified or not checked

token_exchange

The token_exchange grant type is outside the verified path of this guide. With token_exchange, the supervisor first asks the gateway for an intermediate token and sends its JWT-SVID with the request. The gateway needs its own Workload API socket, and it sends its own JWT-SVID to the token endpoint as the client assertion.

Gateway checks on the sandbox identity

With token_exchange, the gateway verifies the issuer, audience, signature, and trust domain of the supervisor’s JWT-SVID against its own JWT-SVID. It does not check the SPIFFE ID path, and it does not compare the SPIFFE ID with the sandbox that calls it. In the final exchange, the supervisor sends its own JWT-SVID to the token endpoint as the client assertion, so Keycloak’s client lookup by sub applies as well. With client_credentials, the gateway never sees the JWT-SVID. Keycloak checks that the SPIFFE ID lies in its configured trust domain, and its client lookup by SPIFFE ID is the only check on the full SPIFFE ID.

Nodes without a SPIRE agent

The scheduler does not place the SPIRE agent and SPIFFE CSI driver Pods on a node with a NoSchedule taint they do not tolerate. A supervisor Pod mounts a csi.spiffe.io volume, which needs the CSI driver registered with the kubelet of its node. This guide does not cover sandboxes on nodes where the SPIRE agent and the CSI driver do not run. Install workload identity shows the tolerations that let both DaemonSets run on tainted nodes.

HTTPS to the target API

The verified path sent requests to the target API over plain HTTP to an in-cluster Service. Write the provider profile describes the sandbox CA that the agent’s client must trust for HTTPS.

Audience mapper

Adding the target API to the token audience with a Keycloak Audience mapper is outside the verified path of this guide. Put the API in the audience describes the mapper.

Token service

This setup is only known to work with Red Hat build of Keycloak as the token service. It relies on the SPIFFE identity provider of Keycloak, which accepts the client assertion type urn:ietf:params:oauth:client-assertion-type:jwt-spiffe and maps the SPIFFE ID in the JWT-SVID to one Keycloak client. OpenShell defaults to the client assertion type urn:ietf:params:oauth:client-assertion-type:jwt-bearer. No other token service was tested.

Preview status

The SPIFFE identity provider is a preview feature of Keycloak and is not fully supported. Keycloak keeps it in preview because the OAuth SPIFFE Client Authentication specification is still a draft. Preview features are disabled by default, are not recommended for production, and may change or be removed in a future release. Install Keycloak enables the feature.

What you must build

A Keycloak client for each sandbox

The registration in this guide puts the sandbox ID into each supervisor’s SPIFFE ID, and Keycloak maps each SPIFFE ID to exactly one client. Every sandbox therefore needs its own Keycloak client, with the sandbox’s SPIFFE ID in jwt.credential.sub. A sandbox gets no token until its client exists. You must automate creating that client for each new sandbox; this guide contains no automation for it. Create a client for each sandbox lists the client settings.

Token validation and access control at the target API

OpenShell rejects token values that are unsafe for an HTTP header but does not validate the token for the target. The API that receives the token must validate its issuer, audience, signature, and expiry. It must also restrict access by the azp claim, which names the Keycloak client that the token was issued for. Protect the target API lists the checks.

A gateway identity and a gateway client for token_exchange

With token_exchange, the gateway needs a SPIFFE ID of its own in the same trust domain as the sandboxes. The registration in this guide does not select the gateway Pod. Without a registration of its own, the gateway Pod gets the fallback ID, which every Pod with the same namespace and ServiceAccount shares. The realm also needs a client whose jwt.credential.sub is the gateway’s SPIFFE ID. Gateway identity and Gateway client for token exchange describe both.

Coming

Change request 2772 in the OpenShell repository proposes the delegated OIDC identity of the user who creates the sandbox as the subject token for token_exchange. The change request is not part of the baseline and may change before it merges.

Delegated identity for token exchange

Experimental: in review

Delegated identity for token exchange is not part of the baseline. It is proposed in change request #2772 (status as of 2026-10-15) and may change or be dropped before it merges.

Change request 2772 proposes the subject-token source sandbox_delegated_identity for the token_exchange grant type. With source: sandbox_delegated_identity in token_grant.subject_token, the subject token of the gateway-brokered intermediate exchange is the delegated OIDC identity of the user who creates the sandbox. A provider for such a profile uses --runtime-credentials.

openshell sandbox create --use-my-identity-for=<duration> enables delegation for one sandbox. The flag accepts positive durations with the suffix m, h, or d, for example 8h. The gateway enforces its configured maximum delegation duration. Delegation must be enabled when the sandbox is created, and a sandbox created without --use-my-identity-for cannot add delegated identity later. The original delegator can extend or withdraw an existing delegation with openshell sandbox delegated-identity extend and withdraw, and openshell sandbox delegated-identity status shows its state.

When the user has no usable gateway-owned authorization, the CLI opens a browser for a separate Authorization Code flow with PKCE that requests only openid and offline_access. The CLI hands the resulting access and refresh tokens to the gateway, and the normal CLI login is separate. The gateway OIDC client must allow the Authorization Code flow, the loopback callback URI of the CLI, and refresh tokens for offline_access.

In the intermediate exchange, the gateway sends its own JWT-SVID to the token endpoint as the client assertion. Delegated identity therefore needs the gateway identity and the gateway client for token exchange that token_exchange needs. Some token services require the aud claim of the delegated access token to include the client identity that the gateway JWT-SVID authenticates. For those, the identity provider (IdP) must add that audience to issued and refreshed delegated access tokens. token_exchange is outside the verified path of this guide, as Known limitations states.

The gateway sends the raw access token of the delegating user as the subject token to the token_endpoint of the provider profile. It loads the current profile for each exchange, so anyone who can change that profile can redirect later exchanges to an endpoint they control. Delegate identity only through providers whose configuration administrators you trust with your delegated access token.
