Configure Keycloak

Keycloak accepts a sandbox’s JWT-SVID only when it trusts the SPIRE signing keys and maps the SPIFFE ID in the SVID to exactly one client. This page creates a realm with a SPIFFE identity provider for the signing keys and describes the client that each sandbox needs. How it works shows where these checks happen in a token grant.

This setup is only known to work with Keycloak. Red Hat build of Keycloak is the only token service it was verified with.

How Keycloak accepts a JWT-SVID

The supervisor sends its JWT-SVID as the client assertion of a client_credentials request, without a client ID. Keycloak handles the request in three steps.

  1. Find the client. For the assertion type urn:ietf:params:oauth:client-assertion-type:jwt-spiffe, Keycloak looks up the enabled client whose attribute jwt.credential.sub equals the sub claim, the sandbox SPIFFE ID. If more than one enabled client matches, the lookup fails.

  2. Find the identity provider. The client’s attribute jwt.credential.issuer holds the alias of the SPIFFE identity provider that verifies the assertion. Keycloak verifies the assertion only for a client whose authenticator type is federated-jwt.

  3. Verify the JWT-SVID. The identity provider rejects a sub outside its trust domain. It fetches the signing keys with an HTTP GET on its bundle endpoint. It accepts exactly one audience, the realm issuer https://<keycloak-host>/realms/<realm>;.

The client_credentials grant also requires a confidential client with service accounts enabled. Keycloak issues the token for the client’s service account user, whose name is service-account- followed by the client ID.

Before you begin

  • Keycloak runs as described in Install Keycloak, with the Keycloak resource keycloak in the namespace keycloak and the host name <keycloak-host>.

  • The SPIRE OIDC discovery provider serves https://oidc-discovery.<apps-domain>; as described in Install workload identity. <trust-domain> is the trust domain configured there.

  • Sandbox supervisors receive the SPIFFE ID spiffe://<trust-domain>/openshell/sandbox/<sandbox-id> as described in Register sandbox identities.

  • You choose <realm>, the name of the realm, for example openshell.

Create the realm and the SPIFFE identity provider

A KeycloakRealmImport resource creates a realm from a realm representation. The realm on this page holds one SPIFFE identity provider, which trusts JWT-SVIDs from the trust domain and reads their signing keys from the SPIRE OIDC discovery provider.

  1. Create the KeycloakRealmImport.

    oc apply -f - <<'EOF'
apiVersion: k8s.keycloak.org/v2beta1
kind: KeycloakRealmImport
metadata:
  name: openshell-realm
  namespace: keycloak
spec:
  keycloakCRName: keycloak
  realm:
    realm: <realm>
    enabled: true
    identityProviders:
      - alias: spiffe
        providerId: spiffe
        enabled: true
        config:
          trustDomain: spiffe://<trust-domain>
          bundleEndpoint: https://oidc-discovery.<apps-domain>/keys
EOF

    keycloakCRName names the Keycloak resource, which must be in the same namespace. realm takes a realm representation. providerId: spiffe selects the SPIFFE identity provider. alias is the name that each client references in its jwt.credential.issuer attribute. trustDomain is the trust domain with the spiffe:// prefix and no trailing slash, because Keycloak accepts only a sub that starts with this value followed by /. Keycloak also rejects a trust domain that is not spiffe:// followed only by lowercase letters, digits, dots, hyphens, and underscores, so a trailing slash fails validation. bundleEndpoint is the HTTPS URL of a SPIFFE bundle endpoint or of an OpenID Connect JWKS endpoint. This page uses the /keys endpoint of the SPIRE OIDC discovery provider, which serves the JSON Web Key Set for JWT validation.

    Keycloak must trust the certificate that the bundle endpoint presents. Its truststore holds the Java default truststore, the Kubernetes service account CA and the OpenShift service CA when they are mounted, and the certificates added through spec.truststores of the Keycloak resource. If no CA in that truststore issued the bundle endpoint’s certificate, add the issuing CA through spec.truststores.

  2. Wait for the import.

    Check: the condition Done is True and the condition HasErrors is False.

    oc get keycloakrealmimport openshell-realm -n keycloak -o jsonpath='{range .status.conditions[*]}{.type}={.status}{" "}{end}'

  3. Check the realm discovery document.

    Check: the token_endpoint is https://<keycloak-host>/realms/<realm>/protocol/openid-connect/token.

    curl -sS "https://<keycloak-host>/realms/<realm>/.well-known/openid-configuration"

The import only creates realms. It does not overwrite an existing realm with the same name, and it does not update or delete a realm. The operator documentation recommends deleting the KeycloakRealmImport after the import, which removes its Job and Pod. Delete it only after both checks pass. The import status check then finds no resource, and the discovery document check remains the durable check of the realm. Only namespace administrators should be able to create or edit KeycloakRealmImport resources.

Create a client for each sandbox

Keycloak maps each SPIFFE ID to one client, and each sandbox has its own SPIFFE ID. A sandbox gets no token until its client exists.

Every sandbox needs its own client in the realm, with its SPIFFE ID in jwt.credential.sub. You must automate creating that client for each new sandbox. Keycloak documents that each client must have a unique SPIFFE ID per realm.

Create the client through the Admin REST API or the Admin Console with the following client representation. Replace <sandbox-id> with the ID of the sandbox.

{
  "clientId": "sandbox-<sandbox-id>",
  "publicClient": false,
  "serviceAccountsEnabled": true,
  "standardFlowEnabled": false,
  "directAccessGrantsEnabled": false,
  "clientAuthenticatorType": "federated-jwt",
  "attributes": {
    "jwt.credential.issuer": "spiffe",
    "jwt.credential.sub": "spiffe://<trust-domain>/openshell/sandbox/<sandbox-id>"
  }
}

clientId is a name you choose, and Keycloak names the service account user service-account-sandbox-<sandbox-id> after it. publicClient: false and serviceAccountsEnabled: true let the client use the client_credentials grant. standardFlowEnabled: false and directAccessGrantsEnabled: false turn off the Authorization Code Flow and Direct Access Grants. clientAuthenticatorType: federated-jwt authenticates the client with an assertion that an identity provider verifies. jwt.credential.issuer is the alias of the SPIFFE identity provider. jwt.credential.sub is the sandbox SPIFFE ID.

Values for the provider profile

A provider profile that obtains tokens from this realm uses these token grant values.

token_endpoint

https://<keycloak-host>/realms/<realm>/protocol/openid-connect/token.

client_assertion_type

urn:ietf:params:oauth:client-assertion-type:jwt-spiffe. OpenShell defaults to urn:ietf:params:oauth:client-assertion-type:jwt-bearer, so the profile must set this value.

jwt_svid_audience

Can stay unset. For a token endpoint with /realms/<realm> in its path, the supervisor derives the audience https://<keycloak-host>/realms/<realm>;, which has the same form as the realm issuer.

Gateway client for token exchange

This section is outside the verified path of this guide, which covers the client_credentials grant type.

With the token_exchange grant type, the gateway sends its own JWT-SVID as the client assertion to the same token endpoint. Keycloak looks up the client for the gateway’s SPIFFE ID in the same way as for a sandbox, so the realm also needs a client whose jwt.credential.sub is the gateway’s SPIFFE ID. Register sandbox identities describes what the gateway identity requires.
