Configure OpenShell

OpenShell needs an implementation of the SPIFFE Workload API, served to Pods through the csi.spiffe.io CSI driver. Sandbox supervisors use it for token grants, and the gateway uses it for token exchange. This guide uses Zero Trust Workload Identity Manager, set up in Install workload identity. This page enables the Workload API socket in the OpenShell Helm chart and checks where it appears.

How OpenShell uses the socket

OpenShell mounts the Workload API socket only when the Kubernetes driver setting provider_spiffe_workload_api_socket_path holds a path. In the Helm chart, the setting belongs to the openshell.drivers.kubernetes table of gatewayConfig, which the chart renders into gateway.toml. An empty or omitted path disables the socket. The chart also accepts server.providerTokenGrants.spiffe as a deprecated alias for this setting. When your values set both, gatewayConfig wins. With the path set, the setting affects three Pods:

Gateway Pod

The chart adds a read-only csi.spiffe.io volume, mounts it at the parent directory of the socket path, and sets OPENSHELL_GATEWAY_SPIFFE_WORKLOAD_API_SOCKET. The gateway reads this socket only for token exchange. It fetches its own JWT-SVID there and verifies supervisor JWT-SVIDs with the JWT bundles from the Workload API. client_credentials grants do not use the gateway socket, but the chart mounts it whenever the socket path is set.

Supervisor Pod

When the driver creates a supervisor Pod, it mounts a read-only csi.spiffe.io volume into the supervisor container at the parent directory of the socket path and sets OPENSHELL_PROVIDER_SPIFFE_WORKLOAD_API_SOCKET. The supervisor fetches its JWT-SVID for a token grant from this socket.

Workload Pod

The workload Pod, which runs the agent, receives no provider identity socket.

Supervisors authenticate to the gateway with sandbox JWTs that the gateway mints, not with SPIFFE. How it works shows the full token grant flow.

Before you begin

  • Zero Trust Workload Identity Manager runs with the SPIRE agent and the SPIFFE CSI driver, as described in Install workload identity.

  • OpenShell 0.1.4 runs on the cluster as the Helm release openshell in <namespace>. The OpenShell OpenShift guide describes this installation.

  • Sandboxes run in <namespace>, the chart default.

  • The gateway runs as the StatefulSet openshell, the chart default, so its Pod is openshell-0.

Enable the Workload API socket

You enable the socket with a Helm upgrade of the existing release. The documented upgrade path reruns helm upgrade --install with the values you installed with, so you add the SPIFFE block to those values.

  1. Save the values of the existing installation to a file.

    helm get values openshell -n '<namespace>' -o yaml > openshell-values.yaml

    If the file contains only null, the release has no user values; replace the content with the block from the next step.

  2. Add the SPIFFE block to openshell-values.yaml. Merge it with the gatewayConfig key if the file already has one.

    gatewayConfig:
  openshell.drivers.kubernetes:
    provider_spiffe_workload_api_socket_path: /spiffe-workload-api/spire-agent.sock

    provider_spiffe_workload_api_socket_path mounts the socket into the gateway Pod and the supervisor Pods, at this path inside them. /spiffe-workload-api/spire-agent.sock is the path in the gateway configuration reference. The CSI driver serves the socket directory of the SPIRE agent, and the socket file in it is spire-agent.sock. The chart and the driver mount the volume at the parent directory of the path, so keep the socket in a dedicated directory. The driver rejects a relative path and a socket directly under /.

  3. Upgrade the release with the merged values.

    helm upgrade --install openshell oci://ghcr.io/nvidia/openshell/helm-chart \
  --version 0.1.4 \
  --namespace '<namespace>' \
  -f openshell-values.yaml

  4. Wait for the gateway to roll out.

    oc -n '<namespace>' rollout status statefulset/openshell

  5. Check the volume of the gateway Pod.

    Check: the gateway Pod has a csi.spiffe.io volume.

    oc -n '<namespace>' get pod openshell-0 -o jsonpath='{.spec.volumes[?(@.csi)].csi.driver}'

  6. Check the socket variable of the gateway.

    Check: OPENSHELL_GATEWAY_SPIFFE_WORKLOAD_API_SOCKET holds the socket path.

    oc -n '<namespace>' get pod openshell-0 -o jsonpath='{.spec.containers[?(@.name=="openshell-gateway")].env[?(@.name=="OPENSHELL_GATEWAY_SPIFFE_WORKLOAD_API_SOCKET")].value}'

Check a sandbox

The driver adds the socket when it creates a supervisor Pod, so run these checks after you create a sandbox. Verify the setup end to end shows how to create a sandbox. <sandbox-id> is the ID of that sandbox in lowercase; copy it from the supervisor Pod name in the first step. The driver names its supervisor Pod os-supervisor-<sandbox-id> and labels its workload Pod with openshell.ai/boundary-role=workload and openshell.ai/boundary-pair=<sandbox-id>.

  1. List the supervisor Pods to find the sandbox ID.

    Check: the list shows a Pod named os-supervisor-<sandbox-id>.

    oc -n '<namespace>' get pods -l openshell.ai/component=supervisor

  2. Check the supervisor Pod.

    Check: the Pod has a csi.spiffe.io volume, and the supervisor container sets OPENSHELL_PROVIDER_SPIFFE_WORKLOAD_API_SOCKET to the socket path.

    oc -n '<namespace>' get pod 'os-supervisor-<sandbox-id>' -o jsonpath='{.spec.volumes[?(@.csi)].csi.driver}{" "}{.spec.containers[?(@.name=="supervisor")].env[?(@.name=="OPENSHELL_PROVIDER_SPIFFE_WORKLOAD_API_SOCKET")].value}'

  3. Check the workload Pod.

    Check: the command lists one Pod, and it has no csi.spiffe.io volume.

    oc -n '<namespace>' get pods -l 'openshell.ai/boundary-role=workload,openshell.ai/boundary-pair=<sandbox-id>' -o jsonpath='{range .items[*]}{.metadata.name}{" csi="}{.spec.volumes[?(@.csi)].csi.driver}{"\n"}{end}'
