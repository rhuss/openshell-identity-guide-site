Administrator guide

An agent in an OpenShell sandbox often needs to call upstream APIs. The usual way to give it access is a provider, which connects a service name to a stored credential that the supervisor hands out only where policy allows it. A token grant instead has the supervisor obtain a short-lived access token from an OAuth2 token service, using the sandbox’s workload identity as the client assertion. With the client_credentials grant that this guide uses, the provider stores no credential at all. In this section you set up that path on OpenShift. At the end, each sandbox supervisor fetches a JWT-SVID from SPIRE, sends it to Keycloak as the client assertion, and injects the access token it receives into the requests that match its provider profile. The supervisor sends no client secret, the Pod that runs the agent receives no identity socket, and the token is not placed in the sandbox environment.

What you set up

OpenShell is a runtime for autonomous AI agents. It lets agents read files, call APIs, and use credentials, while a policy you declare limits what each agent can touch. Each agent runs in a sandbox, an isolated boundary that owns the agent’s processes and forwards its network traffic. The supervisor sits on the trusted side of that boundary: it checks requests against policy, supplies credentials, and opens approved connections. On Kubernetes, the supervisor runs in its own Pod, separate from the Pod that runs the agent.

SPIFFE is a standard for issuing identity to services across heterogeneous environments. A SPIFFE ID is a URI of the form spiffe://<trust-domain>/<path>: the trust domain names the system that issued the identity, and the path names the workload. The identity document that SPIFFE defines is the SVID (SPIFFE Verifiable Identity Document). A JWT-SVID is a signed JWT whose sub claim is the SPIFFE ID of the workload it was issued to. SPIRE is the SPIFFE runtime environment: it attests running software and issues SPIFFE IDs and SVIDs to it through the SPIFFE Workload API. Zero Trust Workload Identity Manager is an OpenShift operator that deploys and manages the SPIRE server, the SPIRE agent, the SPIFFE CSI driver, and the SPIRE OIDC discovery provider.

Keycloak is open source identity and access management that adds authentication to applications and secures services. This guide uses the Red Hat build of Keycloak as the OAuth2 token service, the identity provider (IdP) that the supervisor requests access tokens from. A Keycloak feature called the SPIFFE identity provider authenticates clients with SPIFFE JWT-SVIDs.

Zero Trust Workload Identity Manager runs the SPIRE agent and the SPIFFE CSI driver as DaemonSets, and the CSI driver serves the SPIRE agent’s Workload API socket to Pods. OpenShell mounts that socket into the supervisor Pod, not into the Pod that runs the agent. The supervisor fetches a JWT-SVID over the socket and sends it to the Keycloak token endpoint. Keycloak verifies the JWT-SVID with the signing keys that the SPIRE OIDC discovery provider publishes, and maps its SPIFFE ID to exactly one Keycloak client. Every sandbox therefore needs its own Keycloak client, and you must automate creating that client for each new sandbox. The Configure Keycloak task in the list below describes that client.

Compared with a stored client secret, each JWT-SVID is short-lived and is issued to one attested Pod. The registration this guide creates binds every SPIRE entry to the supervisor Pod’s UID, and a JWT-SVID is valid for five minutes unless its registration entry sets another lifetime. Trust model explains what this attestation proves and what it leaves open. Zero Trust Workload Identity Manager and Keycloak install as operators from the redhat-operators catalog, and OpenShell installs from a Helm chart.

The SPIFFE identity provider is a preview feature of Keycloak and is not fully supported. Preview features are disabled by default, are not recommended for production, and may change or be removed in a future release.

Before you begin

  • You have an OpenShift cluster at version 4.19 or later, with oc configured. OpenShell requires OpenShift 4.19 or later, and the Zero Trust Workload Identity Manager README lists the same minimum.

  • You have access to the cluster with cluster-admin privileges.

  • Your cluster can install operators from the redhat-operators catalog source in openshift-marketplace.

  • Your cluster has a default StorageClass. The SPIRE server, the OpenShell gateway, and every sandbox workspace use volume claims that name no storage class. Without a default StorageClass, the workspace claim stays Pending and the sandbox never starts.

  • OpenShell 0.1.4 runs on the cluster, installed with Helm as the OpenShell OpenShift guide describes. That guide also requires the Agent Sandbox controller and a network plugin that enforces ingress and egress NetworkPolicy in sandbox namespaces.

Tasks

Complete the tasks in this order.

  1. Install workload identity: install Zero Trust Workload Identity Manager and create the SPIRE components that issue JWT-SVIDs.

  2. Install Keycloak: install the Red Hat build of Keycloak with its SPIFFE feature enabled, and expose it through a Route.

  3. Configure OpenShell: enable the Workload API socket for sandbox supervisors in the OpenShell Helm chart.

  4. Register sandbox identities: create the ClusterSPIFFEID registration that gives each sandbox supervisor a SPIFFE ID that names its sandbox.

  5. Configure Keycloak: create a realm whose SPIFFE identity provider trusts the SPIRE signing keys, and see which Keycloak client each sandbox needs and that you must automate creating it.

  6. Protect the target API: check what the API that receives the token must validate and which identity it must authorize on.

  7. Verify the setup end to end: send one request from a sandbox through the whole chain.

Known limitations lists what this guide verified, what it did not, and what you must build yourself.
