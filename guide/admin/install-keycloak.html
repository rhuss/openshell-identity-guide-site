Install Keycloak

Keycloak is the identity provider (IdP) in this guide. Its SPIFFE identity provider authenticates clients with SPIFFE JWT-SVIDs. This page installs the Red Hat build of Keycloak operator, a test database, and one Keycloak instance with the spiffe feature, and exposes the instance through a Route. How it works shows where Keycloak takes part in a token grant.

The commands and manifests on this page ran against Red Hat build of Keycloak 26.6.7 from the stable-v26 channel, with the k8s.keycloak.org/v2beta1 API of the Keycloak resource.

The SPIFFE identity provider is a preview feature of Keycloak and is not fully supported. Federated client authentication is supported, but SPIFFE client authentication stays in preview while its specification is a draft. Preview features are disabled by default, are not recommended for production, and may change or be removed in a future release.

Before you begin

  • You have access to the cluster with cluster-admin privileges.

  • Your cluster can install operators from the redhat-operators catalog source in openshift-marketplace.

  • You know <apps-domain>, the apps domain of the cluster. Install workload identity shows how to read it.

  • You choose <keycloak-host>, the host name of Keycloak under the apps domain, for example keycloak.<apps-domain>. The default ingress controller serves *.<apps-domain>.

  • You choose <db-password>, the password of the database user.

Install the operator

The operator runs in the keycloak namespace and watches only that namespace. The operator documentation states that watching several or all namespaces is not fully supported. In the redhat-operators catalog, the operator package is rhbk-operator. Use the channel that matches the Keycloak version you want. This page uses stable-v26.

  1. Check that the catalog offers the channel.

    Check: the channels of rhbk-operator include stable-v26.

    oc get packagemanifest rhbk-operator -n openshift-marketplace -o jsonpath='{range .status.channels[*]}{.name}{"\n"}{end}'

With installPlanApproval: Automatic, OLM upgrades the operator when a new version is released. With the default Keycloak image, the operator then upgrades Keycloak to the matching version, and the database migration rules out a downgrade. The operator documentation strongly recommends installPlanApproval: Manual, so that every upgrade waits for your approval.

  1. Create the Namespace, the OperatorGroup, and the Subscription.

    oc apply -f - <<'EOF'
apiVersion: v1
kind: Namespace
metadata:
  name: keycloak
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: rhbk-operator
  namespace: keycloak
spec:
  targetNamespaces:
    - keycloak
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: rhbk-operator
  namespace: keycloak
spec:
  channel: stable-v26
  name: rhbk-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Automatic
EOF

  2. Wait for the operator to install. Repeat the command until the rhbk-operator CSV shows Succeeded.

    Check: the CSV whose name starts with rhbk-operator.v reaches the phase Succeeded.

    oc get csv -n keycloak

Create the database

The operator does not manage the database. You provision it yourself. The manifests in this section create a single PostgreSQL Pod from the rhel9/postgresql-16 image.

This database is a test setup. For production, use a managed database, for example a database service of your cloud provider or a database operator.

  1. Create the database Secret, Service, and StatefulSet.

    oc apply -f - <<'EOF'
apiVersion: v1
kind: Secret
metadata:
  name: keycloak-db-secret
  namespace: keycloak
stringData:
  username: keycloak
  password: "<db-password>"
---
apiVersion: v1
kind: Service
metadata:
  name: postgres-db
  namespace: keycloak
spec:
  selector:
    app: postgres-db
  ports:
    - port: 5432
      targetPort: 5432
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres-db
  namespace: keycloak
spec:
  serviceName: postgres-db
  replicas: 1
  selector:
    matchLabels:
      app: postgres-db
  template:
    metadata:
      labels:
        app: postgres-db
    spec:
      containers:
        - name: postgres
          image: registry.redhat.io/rhel9/postgresql-16:latest
          env:
            - name: POSTGRESQL_DATABASE
              value: keycloak
            - name: POSTGRESQL_USER
              valueFrom:
                secretKeyRef: {name: keycloak-db-secret, key: username}
            - name: POSTGRESQL_PASSWORD
              valueFrom:
                secretKeyRef: {name: keycloak-db-secret, key: password}
          ports:
            - containerPort: 5432
          volumeMounts:
            - name: data
              mountPath: /var/lib/pgsql/data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 1Gi
EOF

    The image creates the user POSTGRESQL_USER with the password POSTGRESQL_PASSWORD and the database POSTGRESQL_DATABASE. It keeps the database cluster in /var/lib/pgsql/data, which the StatefulSet backs with a 1Gi volume claim. Keycloak reads the same user name and password from the Secret keycloak-db-secret.

  2. Wait for the database Pod.

    Check: the StatefulSet postgres-db reports one ready replica.

    oc get statefulset postgres-db -n keycloak

Create the Keycloak instance

The Keycloak resource describes one Keycloak deployment. The operator creates a StatefulSet and a Service for it, both named after the resource. The OpenShift router terminates TLS in this setup, so Keycloak serves plain HTTP inside the cluster.

  1. Create the Keycloak resource.

    oc apply -f - <<'EOF'
apiVersion: k8s.keycloak.org/v2beta1
kind: Keycloak
metadata:
  name: keycloak
  namespace: keycloak
spec:
  instances: 1
  features:
    enabled:
      - spiffe
  db:
    vendor: postgres
    host: postgres-db
    database: keycloak
    usernameSecret: {name: keycloak-db-secret, key: username}
    passwordSecret: {name: keycloak-db-secret, key: password}
  http:
    httpEnabled: true
  ingress:
    enabled: false
  hostname:
    hostname: https://<keycloak-host>
  proxy:
    headers: xforwarded
EOF

    features.enabled lists the Keycloak features to enable. spiffe enables the SPIFFE identity provider, which is disabled by default. db points Keycloak at the postgres-db Service and the keycloak database, with the credentials from keycloak-db-secret. http.httpEnabled: true enables the HTTP listener on port 8080. ingress.enabled: false stops the operator from creating its basic Ingress, because a Route replaces it. hostname.hostname is the full URL at which clients reach Keycloak. Keycloak derives the issuer of each realm and the URLs in its discovery documents from it. proxy.headers: xforwarded makes Keycloak accept the X-Forwarded-* headers from the proxy in front of it.

    The operator names the Service keycloak-service and its HTTP port http.

With proxy.headers set, the proxy in front of Keycloak must set and overwrite the X-Forwarded-* headers. The operator documentation states that a misconfiguration leaves Keycloak exposed to security vulnerabilities. It recommends edge or re-encrypt TLS termination, because passthrough TLS does not let the proxy change request headers.

  1. Wait for Keycloak.

    Check: the condition Ready is True and the condition HasErrors is False.

    oc get keycloak keycloak -n keycloak -o jsonpath='{range .status.conditions[*]}{.type}={.status}{" "}{end}'

  2. Check that the server enabled the preview feature. Keycloak logs its enabled preview features at startup.

    Check: the log line lists spiffe.

    oc logs statefulset/keycloak -n keycloak | grep 'Preview features enabled'

Expose Keycloak

An edge Route terminates TLS at the OpenShift router and forwards plain HTTP to the http port of keycloak-service. The Route sets no certificate of its own. OpenShift routers typically configure a default certificate on the wildcard domain for such Routes.

  1. Create the Route.

    oc create route edge keycloak -n keycloak --service=keycloak-service --port=http --hostname=<keycloak-host>

  2. Check the issuer of the master realm. Keycloak serves the OpenID Connect discovery document of each realm at /realms/<realm>/.well-known/openid-configuration.

    Check: the issuer is https://<keycloak-host>/realms/master.

    curl -sS "https://<keycloak-host>/realms/master/.well-known/openid-configuration"

Read the initial admin credentials

The operator generates an initial admin user name and password. It stores them in the Secret keycloak-initial-admin, named after the resource. You use them to sign in to the Admin Console or the Admin REST API.

Change the initial admin credentials and enable multi-factor authentication before production use.

  1. Check that the Secret exists.

    Check: keycloak-initial-admin is a kubernetes.io/basic-auth Secret with two data keys.

    oc get secret keycloak-initial-admin -n keycloak

  2. Read the admin user name.

    oc get secret keycloak-initial-admin -n keycloak -o jsonpath='{.data.username}' | base64 -d

  3. Read the password.

    oc get secret keycloak-initial-admin -n keycloak -o jsonpath='{.data.password}' | base64 -d
