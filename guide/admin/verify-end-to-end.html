Verify the setup end to end

One request from a sandbox exercises the whole chain. The supervisor fetches a JWT-SVID from the local Workload API, Keycloak accepts it as a client assertion and returns an access token, and the supervisor injects that token into the request. When the agent’s request succeeds although the sandbox holds no credential, every part of the setup works. This page uses the Keycloak userinfo endpoint as the target API. The endpoint is protected by a bearer token and returns claims about the user that the token was issued for. How it works shows the chain step by step.

Before you begin

  • You completed the pages from Install workload identity to Configure Keycloak.

  • Keycloak serves HTTP as described in Install Keycloak. The operator names its Service keycloak-service and gives it port 8080 for HTTP.

  • The realm is openshell. If you chose another realm name, replace openshell in the URLs on this page.

  • The openshell CLI operates on your active gateway. Add -g <gateway> to a command to select another gateway.

Create the provider

A provider profile tells the supervisor where to obtain a token and which requests receive it. You attach a provider created from the profile to the sandbox.

  1. Write the provider profile to a file.

    cat > keycloak-token-grant-profile.yaml <<'EOF'
id: keycloak-token-grant
display_name: Keycloak SPIFFE token grant
category: other
credentials:
  - name: access_token
    required: false
    auth_style: bearer
    header_name: Authorization
    token_grant:
      token_endpoint: https://<keycloak-host>/realms/openshell/protocol/openid-connect/token
      client_assertion_type: urn:ietf:params:oauth:client-assertion-type:jwt-spiffe
      scopes: [openid]
endpoints:
  - host: keycloak-service.keycloak.svc.cluster.local
    port: 8080
    protocol: rest
    access: read-only
    enforcement: enforce
binaries:
  - /usr/bin/curl
  - /usr/local/bin/curl
EOF

    id is the value that openshell provider create --type takes. category is informational. required: false makes the credential optional, so the provider needs no stored value for it. auth_style: bearer with header_name: Authorization injects the token as Authorization: Bearer <token>. token_grant holds the values from Values for the provider profile, with jwt_svid_audience unset. scopes: [openid] requests the openid scope, because the userinfo endpoint rejects a token without it. endpoints names the Keycloak Service inside the cluster, and the supervisor injects the token only into requests to this endpoint. protocol: rest turns on request inspection. access: read-only allows GET, HEAD, and OPTIONS, and enforcement: enforce blocks requests that break these rules. binaries lists the executables that may reach the endpoint.

  2. Lint the profile before you import it. Lint asks the gateway to check the profile without storing it. It reports an error when the workspace already holds a profile with this id.

    openshell profile lint -f keycloak-token-grant-profile.yaml

  3. Import the profile into the current workspace.

    openshell profile import -f keycloak-token-grant-profile.yaml

  4. Create the provider. Create providers for token-grant-only profiles with --runtime-credentials, as the OpenShell documentation instructs. The flag records the provider without stored credentials and makes explicit that the credential is resolved at runtime.

    openshell provider create --name keycloak-token-grant --type keycloak-token-grant --runtime-credentials

  5. Check the provider.

    Check: the provider keycloak-token-grant has the type keycloak-token-grant.

    openshell provider get keycloak-token-grant

Create the sandbox

The sandbox runs curl, so its image must contain curl. This page uses the community base image ghcr.io/nvidia/openshell-community/sandboxes/base:latest. OpenShell uses a policy that ships in an image only when the sandbox has no policy of its own, and a sandbox with an invalid image policy does not start. The command on this page passes its own policy with --policy.

  1. Write the sandbox policy to a file.

    cat > sandbox-policy.yaml <<'EOF'
version: 1

filesystem_policy:
  include_workdir: true
  read_only:
    - /usr
    - /lib
    - /proc
    - /dev/urandom
    - /app
    - /etc
    - /var/log
  read_write:
    - /sandbox
    - /tmp
    - /dev/null

landlock:
  compatibility: best_effort

process:
  run_as_user: sandbox
  run_as_group: sandbox
EOF

    The policy sets only filesystem, Landlock, and process settings. include_workdir, read_only, and read_write set the paths the workload can read and write, and process names the user and group of the workload. With compatibility: best_effort, the sandbox runs without the filesystem rules and logs a high-severity finding when none of the listed paths can be applied or Landlock fails to enforce the rules. It has no network_policies, because the attached provider adds the network rule for the Keycloak endpoint to the effective policy.

  2. Create the sandbox from the image, with the provider attached. --detach keeps the CLI from attaching to the sandbox’s main process.

    openshell sandbox create --name idtest --provider keycloak-token-grant --from ghcr.io/nvidia/openshell-community/sandboxes/base:latest --policy sandbox-policy.yaml --detach

  3. Wait until the sandbox is ready, and note its ID. Repeat the command until the phase is Ready. The Id line shows the sandbox ID, a UUID, which this page calls <sandbox-id>.

    Check: the phase is Ready, and the Id line shows a UUID.

    openshell sandbox get idtest

A sandbox without its own Keycloak client gets no token. Keycloak finds no client for the sandbox’s SPIFFE ID and rejects the assertion, and the supervisor answers the agent’s request with HTTP 502 without forwarding it.

  1. Create the Keycloak client sandbox-<sandbox-id> for this sandbox as described in Create a client for each sandbox.

Send a request from the sandbox

The request leaves the sandbox without a credential. The supervisor obtains the token and adds it before it forwards the request to Keycloak.

  1. Call the userinfo endpoint from inside the sandbox.

    Check: Keycloak answers with HTTP 200, and preferred_username is service-account-sandbox-<sandbox-id>, the service account user of the sandbox’s client.

    openshell sandbox exec --name idtest --no-tty -- curl -sS -i http://keycloak-service.keycloak.svc.cluster.local:8080/realms/openshell/protocol/openid-connect/userinfo

  2. Read the sandbox log. OpenShell names the network rule of an attached provider provider followed by the provider name. In that name, OpenShell lowercases ASCII letters, turns every character other than an ASCII letter, a digit, or into , and trims leading and trailing _, so keycloak-token-grant becomes keycloak_token_grant.

    Check: an HTTP:GET event for userinfo shows ALLOWED and the tag [policy:_provider_keycloak_token_grant engine:l7].

    openshell logs idtest

  3. Read the environment of the sandbox.

    Check: the environment holds no access token and no SPIFFE variable.

    openshell sandbox exec --name idtest --no-tty -- env

  4. Check that the sandbox has no Workload API socket. The driver mounts the socket directory /spiffe-workload-api only into the supervisor container.

    Check: the path does not exist, so test exits with status 1.

    openshell sandbox exec --name idtest --no-tty -- test -e /spiffe-workload-api

  5. Send the same userinfo request through the Keycloak Route from Install Keycloak, from outside the sandbox and without a token.

    Check: the userinfo endpoint answers with HTTP status 401.

    curl -sS -o /dev/null -w '%{http_code}' "https://<keycloak-host>/realms/openshell/protocol/openid-connect/userinfo"

Only the supervisor adds the token, and the token stays out of the sandbox environment. Protect the target API describes what your own API must check in the token it receives.
