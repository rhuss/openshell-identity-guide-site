OpenShell Workload Identity with SPIFFE and SPIRE

OpenShell is a runtime for autonomous AI agents, and it runs each agent in a sandbox, an isolated boundary around the agent’s processes. Agents often need to call APIs that expect an access token, and OpenShell usually grants that access with a stored credential. This guide sets up the alternative: each sandbox proves its workload identity, an identity issued to running software, and receives a short-lived access token from an OAuth2 token service in return. That only works if the token service trusts the identity and the identity names the right sandbox and nothing else. At the end, SPIRE, which identifies running workloads and issues identities to them, gives each sandbox a signed identity on OpenShift. Red Hat build of Keycloak, the token service, accepts that identity and issues an access token, and OpenShell adds the token to the agent’s requests to your API. With the OAuth2 client_credentials grant that this guide uses, OpenShell stores no credential for the API and sends no client secret.

What the parts are

OpenShell

A runtime for autonomous AI agents. Agents work with files, APIs, and credentials, and a policy that you declare for each agent sets what it may touch. Agents never see real credentials; OpenShell adds them only to requests bound for approved endpoints.

Sandbox

The isolated boundary an agent runs in. It owns the agent’s processes and forwards the agent’s network traffic.

Supervisor

The OpenShell process on the trusted side of the sandbox boundary, to which the sandbox forwards the agent’s network traffic. It checks requests against policy, supplies credentials, and opens approved connections. On Kubernetes, the supervisor has its own Pod, apart from the agent’s Pod.

Gateway

The OpenShell control plane: it manages the lifecycle of sandboxes, delivers policy and settings, and attaches providers. The supervisor loads its policy and provider state from the gateway.

Provider and token grant

A provider connects a service name to a stored credential, which the supervisor hands out only where policy allows it. A token grant is a provider flow that injects a short-lived access token instead. The supervisor sends the sandbox’s identity to an OAuth2 token service as the client assertion, the signed token that authenticates the client in place of a client secret. It injects the access token it receives into the requests that match the provider. With the client_credentials grant type, the supervisor sends the assertion straight to the token service. With the token_exchange grant type, the gateway first brokers an intermediate token for the supervisor.

SPIFFE

A standard for bootstrapping and issuing identity to services across heterogeneous environments. It names a workload with a SPIFFE ID, a URI of the form spiffe://<trust-domain>/<path>, where the trust domain names the system that issued the identity and the path names the workload. The identity document that SPIFFE defines is the SVID (SPIFFE Verifiable Identity Document). A JWT-SVID is a signed JWT whose sub claim is the SPIFFE ID of the workload it was issued to.

SPIRE

The SPIFFE runtime environment. It attests running software, which on Kubernetes means it identifies the Pod that calls it with information from the node’s kubelet. It then issues SPIFFE IDs and SVIDs to that software through the SPIFFE Workload API, the API through which workloads receive their SVIDs. A registration tells SPIRE which Pods receive which SPIFFE ID, as one registration entry per Pod.

Zero Trust Workload Identity Manager

An OpenShift operator that deploys and manages SPIRE. It runs the SPIRE server, and it runs the SPIRE agent as a DaemonSet. It also runs the SPIFFE CSI driver, which serves the agent’s Workload API socket to Pods as a volume, and the SPIRE OIDC discovery provider, which publishes the keys that verify JWT-SVIDs.

Red Hat build of Keycloak

Keycloak is open source identity and access management that adds authentication to applications and secures services. In this guide, the Red Hat build of Keycloak is the OAuth2 token service, the identity provider (IdP) that issues the access tokens. Its SPIFFE identity provider feature lets clients authenticate with SPIFFE JWT-SVIDs.

How they fit together

OpenShell mounts the Workload API socket that the SPIFFE CSI driver serves into the supervisor Pod; the Pod that runs the agent receives no identity socket. When the agent sends a request to an endpoint of a token grant provider, the supervisor intercepts it and looks for a cached access token. Without one, it fetches a JWT-SVID over the socket (step 1 in the diagram) and sends it to the Keycloak token endpoint as the client assertion (step 2). Keycloak looks up the one client whose SPIFFE ID matches the sub claim and verifies the signature with the keys that the SPIRE OIDC discovery provider publishes (step 3). Keycloak then returns an access token, which the supervisor caches (step 4). The supervisor injects the token into the agent’s request and forwards it to the protected API, the API your agent calls (step 5). With client_credentials, the gateway is not on this path; it supplies the supervisor’s policy and provider state.

Why this combination

The obvious alternative is a client secret stored in a provider. In this setup, each JWT-SVID is short-lived and is issued to one attested Pod instead. By default a JWT-SVID expires after five minutes, and a registration entry can set a different lifetime. The registration in this guide binds each of its entries to the UID of the supervisor Pod, so SPIRE serves the JWT-SVID only to that Pod. Keycloak’s federated client authentication removes the need to assign and manage a secret for each client, and with client_credentials the supervisor sends only its JWT-SVID. OpenShell also keeps the access token out of the sandbox environment. You install Zero Trust Workload Identity Manager and Keycloak through operators from the redhat-operators catalog, and OpenShell through its Helm chart.

The verified path

This guide covers one path: the client_credentials grant type with Red Hat build of Keycloak on OpenShift. The end-to-end run used OpenShell 0.1.4, Zero Trust Workload Identity Manager 1.1.2, and Red Hat build of Keycloak 26.6.7. The token_exchange grant type was not verified. The Administrator guide sets up this path, from Install workload identity to Verify the setup end to end.

Status and limits

The SPIFFE identity provider is a preview feature of Keycloak and is not fully supported. Preview features are disabled by default, are not recommended for production, and may change or be removed in a future release.
What the identity proves

The Pod UID that binds a JWT-SVID to its Pod is not part of the SPIFFE ID. In the registration this guide creates, the sandbox part of the SPIFFE ID comes from a Pod annotation, and SPIRE does not attest annotations. The registration also requires the Pod name to be os-supervisor- followed by that annotation value, which ties the annotation to the name of the attested Pod. The sandbox part names the right sandbox only while untrusted users cannot create or patch Pods in the sandbox namespace. A restarted sandbox gets a new supervisor Pod with the same SPIFFE ID, so the SPIFFE ID names a sandbox, not one Pod. With client_credentials, the gateway never sees the JWT-SVID, and Keycloak’s client lookup is the only check on the full SPIFFE ID. With token_exchange, the gateway checks the issuer, audience, signature, and trust domain of the JWT-SVID, not the path of the SPIFFE ID. Trust model explains what the identity proves and why sandbox namespaces must stay administrative.

Token service

The setup depends on the Keycloak SPIFFE identity provider and its client assertion type urn:ietf:params:oauth:client-assertion-type:jwt-spiffe, so Red Hat build of Keycloak is the only token service it is known to work with.

One Keycloak client per sandbox

Because Keycloak resolves each sandbox’s SPIFFE ID to exactly one client, every new sandbox needs its own Keycloak client, and creating it is a step you must automate (Create a client for each sandbox).

Token checks at your API

OpenShell rejects token values that are unsafe for an HTTP header but does not validate the token for the target. The protected API must validate its issuer, audience, signature, and expiry and authorize requests by its azp claim, the Keycloak client it was issued for (Protect the target API).
