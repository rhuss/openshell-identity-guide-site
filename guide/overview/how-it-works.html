How it works

This page follows one token grant from a sandbox to the API it protects. A token grant is the OpenShell provider flow in which the sandbox supervisor obtains a short-lived access token from an OAuth2 token service, using the sandbox’s SPIFFE JWT-SVID as the client assertion. The token service here is Keycloak, the identity provider (IdP). The page covers where the identity socket lives, the five steps of the client_credentials grant, and what the OpenShell gateway checks on a JWT-SVID.

A SPIFFE ID is a URI of the form spiffe://<trust-domain>/<path>. The trust domain names the system that issued the identity, and the path names the workload inside it. A JWT-SVID is a signed JWT whose sub claim is the SPIFFE ID of the workload it was issued to.

The two Pods of a sandbox

The OpenShell gateway is the control plane that manages the lifecycle of sandboxes. A sandbox is the boundary the agent runs in. It owns the agent’s processes and forwards the agent’s network traffic to the supervisor. The supervisor sits on the trusted side of that boundary: it checks requests against policy, supplies credentials, and opens approved connections.

On Kubernetes, the sandbox and the supervisor run in separate Pods. The workload Pod runs openshell-sandbox and the agent process. A second Pod, managed directly by the Kubernetes driver, runs openshell-supervisor. The supervisor authenticates to the gateway, loads policy and provider state, authorizes each destination, and opens the upstream connections. The driver creates a namespace-wide NetworkPolicy that denies all workload egress, so the agent’s traffic leaves the sandbox only through the supervisor.

Of the two Pods of a sandbox, only the supervisor Pod receives the identity socket. Zero Trust Workload Identity Manager runs the SPIRE agent and the SPIFFE CSI driver as DaemonSets, and the CSI driver serves the SPIRE agent’s Workload API socket to Pods as a volume. When the driver setting provider_spiffe_workload_api_socket_path is set, the driver adds a read-only csi.spiffe.io volume to the supervisor container, mounted at the socket’s parent directory. It also sets OPENSHELL_PROVIDER_SPIFFE_WORKLOAD_API_SOCKET to the socket path. An empty value disables the mount. The workload Pod receives no provider identity socket and no gateway credential. The Helm chart also mounts the socket into the gateway Pod, which uses it only for token_exchange.

The client_credentials sequence

Arrow 5 shows the agent’s request, which the supervisor holds from step 1 until it has a token, then forwards with the token injected.

  1. The supervisor fetches a JWT-SVID. The agent sends an HTTP request to an endpoint that a provider profile declares. The supervisor intercepts it and looks for a cached access token. On a cache miss, it requests a JWT-SVID from the SPIRE agent over the mounted Workload API socket. The JWT-SVID audience is jwt_svid_audience from the profile. Without that field, the supervisor derives the audience from the token endpoint: for a token endpoint whose path contains /realms/<realm>/, it keeps the part up to /realms/<realm>, and for other URLs it uses the full token endpoint.

  2. The supervisor sends the JWT-SVID as client assertion. The supervisor POSTs to token_endpoint with grant_type=client_credentials, client_assertion_type, and the JWT-SVID as client_assertion. The request carries no client_id and no client secret. OpenShell defaults client_assertion_type to urn:ietf:params:oauth:client-assertion-type:jwt-bearer. The Keycloak SPIFFE identity provider accepts only urn:ietf:params:oauth:client-assertion-type:jwt-spiffe, so a profile for Keycloak sets that value.

  3. Keycloak verifies the JWT-SVID. Keycloak looks up the client whose federated JWT credential subject equals the assertion’s sub, the SPIFFE ID. That client names the SPIFFE identity provider that verifies the assertion. The identity provider rejects a sub outside its configured trust domain. It accepts exactly one audience, the realm issuer URL <base>/realms/<realm>. For a Keycloak token endpoint, the audience the supervisor derives in step 1 has this same <base>/realms/<realm> form. It checks the signature with keys fetched by an HTTP GET on its bundle endpoint. This guide sets the bundle endpoint to the /keys endpoint of the SPIRE OIDC discovery provider, which serves the JSON Web Key Set for JWT validation.

  4. Keycloak returns an access token. The token endpoint answers with an access token. The supervisor caches it for cache_ttl when the profile sets one, and otherwise for the expires_in of the token response, at most one hour, minus 30 seconds. When the response gives no positive expires_in, the supervisor caches the token for five minutes minus 30 seconds.

  5. The supervisor injects the token. The supervisor writes the token into the request: Authorization: Bearer <token> by default, or the raw token in a custom header with auth_style: header. Injection replaces every agent-supplied instance of that header. The supervisor then forwards the request upstream. A failed grant returns HTTP 502, and the request is not forwarded. The access token is not placed in the sandbox environment.

Step 3 is where the full SPIFFE ID counts. Keycloak maps the sub to exactly one client: when more than one enabled client matches, the lookup fails. Keycloak documents that each client must have a unique SPIFFE ID per realm. Every sandbox SPIFFE ID therefore needs its own Keycloak client, and creating those clients is a requirement the operator must automate.

What the gateway checks

With client_credentials, the gateway is not on the token request path. The supervisor sends the JWT-SVID directly to token_endpoint. The gateway supplies the provider state and the token_grant_owner metadata, which names the policy endpoint that may grant a credential. The supervisor requires that endpoint to admit the request before it acquires a token.

The gateway sees a JWT-SVID only with the token_exchange grant type, where it brokers an intermediate token for the supervisor. That flow requires a Workload API socket on the gateway as well. The gateway accepts the request only from a sandbox principal and only when the requested provider is attached to that sandbox. It then verifies the supervisor’s JWT-SVID against its own:

  • The issuer equals the issuer of the gateway’s JWT-SVID.

  • The audience contains the JWT-SVID audience of the token grant.

  • The signature verifies against the JWT bundles from the gateway’s Workload API.

  • The trust domain equals the gateway’s trust domain.

The gateway does not check the path of the SPIFFE ID, and it does not compare the SPIFFE ID with the calling sandbox. A JWT-SVID with the same issuer and trust domain, the right audience, and a valid signature passes, whichever workload its path names. The gateway uses the verified sub as the audience of the intermediate token.
