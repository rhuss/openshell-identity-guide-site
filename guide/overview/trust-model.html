Trust model

A sandbox’s JWT-SVID carries one identity value: the SPIFFE ID in its sub claim. SPIRE issues the JWT-SVID only to a workload that matches a registration entry, and the entry binds it to one Pod by its Pod UID. The Pod UID is attested, but it is not part of the SPIFFE ID, and relying parties never see it. The sandbox segment of the SPIFFE ID comes from a Pod annotation that the Pod creator writes, and no relying party checks it. What a JWT-SVID proves about a sandbox therefore depends on how tightly the registration selects Pods and on who can create or patch Pods in the sandbox namespace. It also depends on who can create or change ClusterSPIFFEID resources, which are cluster-scoped and set the SPIFFE ID of every Pod they select. The relying parties in this guide are Keycloak and, with the token_exchange grant type, the OpenShell gateway. This page separates what binds the identity from what names it, states how unique each value is, and explains why sandbox namespaces must stay administrative. For the token flow itself, see How it works.

What SPIRE attests

The k8s workload attestor of the SPIRE agent generates Kubernetes selectors for each workload that calls the agent. It finds the workload’s Pod through the calling process’s cgroup membership and then asks the kubelet about that Pod. Its selectors include the namespace (k8s:ns), the ServiceAccount (k8s:sa), Pod labels (k8s:pod-label), the container name (k8s:container-name), the Pod name (k8s:pod-name), and the Pod UID (k8s:pod-uid). Pod annotations are not among them.

A registration entry decides which of these selectors must match. SPIRE Controller Manager renders one entry for each Pod that a ClusterSPIFFEID selects. Every such entry carries k8s:pod-uid:<pod-uid>, and its parent ID names the node the Pod runs on. The controller manager adds the selectors that the workloadSelectorTemplates field renders. The sandbox registration in this guide adds k8s:container-name:supervisor and a Pod-name selector rendered from the sandbox ID annotation: k8s:pod-name:os-supervisor-{{ index .PodMeta.Annotations "openshell.ai/sandbox-id" }}. The driver names the supervisor container supervisor and the supervisor Pod os-supervisor-<sandbox-id>. SPIRE therefore serves the entry only to a Pod whose actual name is os-supervisor- followed by its own annotation value. A Pod name must be unique within a namespace and cannot be updated. Because the registration covers only the sandbox namespace, at most one live Pod at a time can attest for a given sandbox ID. Another Pod can take the name os-supervisor-<sandbox-id> only while the real supervisor Pod does not exist, for example while the sandbox is stopped.

Kubernetes generates the Pod UID when it creates the Pod. The Kubernetes API describes the UID as unique in time and space, populated by the system, and read-only. The Pod creator does not choose it.

With this guide’s registration, attestation answers one question: does the caller run in the supervisor container of the Pod with this UID and name? The Pod UID binds the entry, but the SPIFFE ID does not contain it. A relying party sees the SPIFFE ID in the sub claim and nothing about the Pod.

What names the identity

The SPIFFE ID in an entry comes from the spiffeIDTemplate of the ClusterSPIFFEID. The template can read the trust domain, the Pod metadata, and the Pod spec, among other data. The podSelector and namespaceSelector fields choose the Pods by label.

Each segment of spiffe://<trust-domain>/openshell/sandbox/<sandbox-id> has a different source:

  • <trust-domain> is the trust domain the controller manager operates for, inserted by {{ .TrustDomain }}. Keycloak rejects a sub outside its configured trust domain, and with token_exchange the gateway requires the trust domain of its own JWT-SVID.

  • /openshell/sandbox/ is fixed text that the author of the ClusterSPIFFEID chose.

  • <sandbox-id> is the value of the Pod’s openshell.ai/sandbox-id annotation, which the Pod creator writes. No relying party checks it, but the Pod-name selector ties it to the name of the attested Pod.

The sandbox registration in this guide selects Pods in the sandbox namespace that carry the labels openshell.ai/managed-by: openshell, openshell.ai/component: supervisor, and openshell.ai/boundary-role: supervisor. The OpenShell gateway’s Kubernetes driver creates the supervisor Pod and writes these labels and the annotation.

The driver also writes the openshell.ai/sandbox-id annotation into the workload Pod template, with the sandbox’s own ID, after any annotations from the sandbox template. A sandbox creator can put other openshell.ai/ labels on the workload Pod through the sandbox template, because the gateway checks template labels and annotations only for count and size and the driver writes them unchanged into the workload Pod template. The driver overwrites openshell.ai/boundary-role with workload in that template and checks that value again on the admitted Pod. That label keeps the workload Pod out of the sandbox registration, and the container-name and Pod-name selectors require the supervisor’s container and Pod name on top. The driver also removes any spiffe-workload-api volume and mount from the workload Pod, and caller resource admission accepts only emptyDir, downwardAPI, persistentVolumeClaim, and the generation’s own Secret volumes.

Labels and annotations hold whatever the Pod creator wrote. The SPIRE agent reports labels as the creator set them and emits no selector for annotations.

Pod UID

Stop deletes the workload Pod and the supervisor Pod. Start creates a new supervisor Pod for the same sandbox. The new Pod has a new UID, and the controller manager renders a new entry for it. The SPIFFE ID stays the same because the driver writes the same sandbox ID on the new Pod. The Pod UID identifies one supervisor Pod of a sandbox, while the SPIFFE ID that relying parties see does not change across a restart.

Sandbox ID

The gateway generates the sandbox ID as a random UUID when it creates the sandbox. Each sandbox has one sandbox ID, and the driver writes it on every supervisor Pod of that sandbox. That makes the sandbox ID unique per sandbox only while the driver is the sole writer of the annotation on Pods that the registration selects.

Fallback identity

Zero Trust Workload Identity Manager creates a fallback ClusterSPIFFEID named zero-trust-workload-identity-manager-spire-default. Its template is spiffe://<trust-domain>/ns/<ns>/sa/<sa>, and it sets fallback: true. A fallback applies only when no other non-fallback ClusterSPIFFEID matches the Pod. Its namespace selector excludes the operator’s own namespace, and the controller manager ignores kube-system, kube-public, local-path-storage, and openshift-*. In all other namespaces, every Pod that no registration selects gets this ID, including the workload Pod of each sandbox.

The fallback ID depends only on the namespace and the ServiceAccount. The Kubernetes driver assigns one configured ServiceAccount to the workload and supervisor Pods of every sandbox, and in managed mode it creates that ServiceAccount in each workspace namespace. All workload Pods in a sandbox namespace share one fallback SPIFFE ID, and that ID names no sandbox.

One Keycloak client per SPIFFE ID

Keycloak finds the client for a client assertion by its sub, the SPIFFE ID. The lookup reads at most two enabled clients whose federated JWT credential subject matches. When it finds more than one, it fails with "Multiple clients matches attributes". Keycloak documents that each client must have a unique SPIFFE ID per realm. Each sandbox SPIFFE ID needs exactly one Keycloak client. Every Pod that holds a given SPIFFE ID authenticates as that same client, so a shared fallback ID cannot tell sandboxes apart at Keycloak.

What the relying parties check

With the client_credentials grant type, the gateway never sees the JWT-SVID. The supervisor sends it directly to the token endpoint. Keycloak checks that the sub lies in its configured trust domain, and its client lookup by sub is the only check on the full SPIFFE ID.

With token_exchange, the gateway verifies the supervisor’s JWT-SVID issuer, audience, signature, and trust domain against its own JWT-SVID. It does not check the SPIFFE ID path. In the final exchange, the supervisor sends its own JWT-SVID to the token endpoint as the client assertion, so Keycloak’s client lookup by sub applies as well.

No relying party compares the <sandbox-id> segment with the sandbox that runs in the attested Pod. That segment is only as trustworthy as the registration that selects the Pod and the access control that limits who creates or patches Pods in the sandbox namespace.

Why sandbox namespaces must stay administrative

The Kubernetes driver requires sandbox namespaces to stay administrative. Untrusted principals must not create permissive network policies, create Pods, read bootstrap Secrets, or spoof the OpenShell role labels there. In the shared and managed workspace modes, only the driver and its trusted Agent Sandbox controller may administer the sandbox namespace, the Sandbox resources, the sandbox Pods, or the configured sandbox ServiceAccount. In operator mode, the platform operator owns the namespace lifecycle and must keep other principals from creating or changing Sandbox resources, creating sandbox Pods with fabricated owner references, or using the configured sandbox ServiceAccount.

Two exposures remain with this guide’s registration:

  • Anyone with Kubernetes permission to create Pods in a sandbox namespace can set the supervisor labels, the container name, the Pod name, and any openshell.ai/sandbox-id value, and permission to patch Pods changes their labels and annotations. The controller manager then registers such a Pod under the named sandbox’s SPIFFE ID, and SPIRE attests it by its own Pod UID when its name is os-supervisor- followed by its annotation value. In the shared and managed workspace modes, only the driver and the Agent Sandbox controller may hold that permission; in operator mode, the platform operator must keep it from other principals.

  • The fallback ID spiffe://<trust-domain>/ns/<ns>/sa/<sa> covers the workload Pods of a sandbox namespace and names no sandbox. No Keycloak client or other relying party may accept it.
