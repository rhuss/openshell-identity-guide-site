Get short-lived tokens for your API

Your agent needs to call your API, and your API wants a bearer token. You could put a secret into the sandbox, but you don’t have to. A provider with a token grant lets the sandbox supervisor fetch a short-lived token from Keycloak when the agent calls your API. The supervisor proves the sandbox’s identity with a SPIFFE JWT-SVID, so the provider stores no credential at all. It adds the token to the request on the way out, and the token never lands in the agent’s environment.

On this page you write a provider profile for your API, turn it into a provider, and attach the provider to a new sandbox. Then you send one request and check that the token arrived.

Before you begin

  • Your administrator has set up the platform as described in the Administrator guide.

  • You know the Keycloak host and the realm that your administrator uses. This page calls them <keycloak-host> and <realm>.

  • Your API accepts access tokens from that realm. Protect the target API describes what the API checks.

  • The openshell CLI operates on your active gateway. Add -g <gateway> to a command to select another gateway.

Write the provider profile

A provider profile answers three questions. Where does the supervisor get the token, which requests receive it, and which programs may send those requests?

  1. Write the profile to a file, and replace the placeholders with your own values.

    cat > api-token-profile.yaml <<'EOF'
id: <profile-id>
display_name: Token grant for my API
category: other
credentials:
  - name: access_token
    required: false
    auth_style: bearer
    header_name: Authorization
    token_grant:
      token_endpoint: https://<keycloak-host>/realms/<realm>/protocol/openid-connect/token
      client_assertion_type: urn:ietf:params:oauth:client-assertion-type:jwt-spiffe
      scopes: [<scope>]
endpoints:
  - host: <api-host>
    port: <api-port>
    protocol: rest
    access: read-only
    enforcement: enforce
binaries:
  - /usr/bin/curl
  - <client-binary>
EOF

Let’s walk through the fields.

id

The profile ID, in lowercase kebab-case with a-z, 0-9, and -. It is also the provider type, the value of --type when you create the provider.

category

Informational only.

required: false

Makes the credential optional, so the provider needs no stored value.

auth_style: bearer with header_name: Authorization

Injects the token as Authorization: Bearer <token>. It replaces any Authorization header that the agent sent.

token_endpoint

The token endpoint of your realm.

client_assertion_type

The SPIFFE assertion type that Keycloak expects.

scopes

The scopes your API expects. The supervisor sends them as one space-separated scope parameter.

jwt_svid_audience

Stays unset. For a token endpoint with /realms/<realm> in its path, the supervisor derives the audience https://<keycloak-host>/realms/<realm>;.

endpoints

The host and port of your API, as the agent calls it. The supervisor injects the token only into requests to these endpoints. protocol: rest turns on request inspection. access picks a preset. read-only allows GET, HEAD, and OPTIONS, read-write adds POST, PUT, and PATCH, and full allows all methods and paths. enforcement: enforce blocks requests that break these rules.

binaries

The executables that may reach your API. /usr/bin/curl is there for the test request at the end of this page. If your image has curl at another path, use that path. <client-binary> is the executable that opens the connection to your API. That’s not always the command you run. A Python or Node.js script runs as its interpreter, so list the interpreter, such as /usr/bin/python3.12. List the real path, not a symlink, and find it with readlink -f inside the sandbox. A listed binary also covers the processes it starts.

Keep client_assertion_type set to urn:ietf:params:oauth:client-assertion-type:jwt-spiffe. OpenShell defaults to urn:ietf:params:oauth:client-assertion-type:jwt-bearer, and the Keycloak SPIFFE identity provider accepts only the jwt-spiffe type. With the default, your sandbox gets no token.

You’ll notice that the endpoint has no tls field. Leave it out. OpenShell then terminates TLS itself, and that’s how it can inspect the request and add the header. The only value the field accepts is skip, and a profile with a token grant rejects skip because it bypasses the header injection.

The agent calls your API with its normal URL. The proxy detects TLS on each tunnel and terminates it with a CA that OpenShell generates for the sandbox. So with an https:// URL, the agent’s client must trust that sandbox CA. OpenShell provides it to the agent’s processes through the variables NODE_EXTRA_CA_CERTS, DENO_CERT, SSL_CERT_FILE, REQUESTS_CA_BUNDLE, CURL_CA_BUNDLE, and GIT_SSL_CAINFO. HTTPS to your API is outside the verified path of this guide, which tested the flow only with plain HTTP to an in-cluster Service.

Create the provider

Now you hand the profile to the gateway and create a provider from it.

  1. Lint the profile. Lint asks the gateway to check the profile without storing it. It also reports an error when your workspace already holds a profile with this id, so run it before you import.

    openshell profile lint -f api-token-profile.yaml

  2. Import the profile into your current workspace.

    openshell profile import -f api-token-profile.yaml

  3. Create the provider with --runtime-credentials, as OpenShell recommends for profiles whose only credentials come from token grants. The flag records the provider without stored credentials and makes explicit that the credential is resolved at runtime.

    openshell provider create --name "<provider-name>" --type "<profile-id>" --runtime-credentials

  4. Look at the provider.

    Check: the output shows the name <provider-name> and the type <profile-id>.

    openshell provider get "<provider-name>"

Create the sandbox

The sandbox runs your agent’s client, so its image has to contain that client.

The image must contain the programs that send the requests, at the paths the profile lists. A profile whose binaries don’t match the image still shows up in the catalog, but its token isn’t injected and its traffic is denied.

OpenShell uses a policy that ships in the image at /etc/openshell/policy.yaml only when the sandbox has no policy of its own. If that image policy is invalid, the sandbox doesn’t start, and OpenShell doesn’t fall back to the default policy. Passing your own policy with --policy avoids the image policy.

  1. Create the sandbox with the provider attached. <image> is your sandbox image, and <policy-file> is your sandbox policy. Verify the setup end to end shows a minimal policy. Your policy needs no network rule for your API, because the attached provider adds that rule to the sandbox’s effective policy. --detach keeps the CLI from attaching to the sandbox’s main process.

    openshell sandbox create --name "<sandbox-name>" --provider "<provider-name>" --from "<image>" --policy "<policy-file>" --detach

  2. Wait until the sandbox is ready, and note its ID. Repeat the command until the phase is Ready. The Id line shows the sandbox ID, a UUID.

    Check: the phase is Ready, and the Id line shows a UUID.

    openshell sandbox get "<sandbox-name>"

Every sandbox needs its own client in the Keycloak realm. Ask your administrator to register the Keycloak client for your sandbox, and give them the sandbox ID. Configure Keycloak describes that client. Until the client exists, Keycloak rejects the sandbox’s assertion, and the supervisor answers your agent’s requests with HTTP 502 without forwarding them.

Send a request

Let’s try it. The request leaves the agent without a credential, and the supervisor adds the token before it forwards the request to your API.

  1. Call your API from inside the sandbox. <api-url> is the URL of a GET endpoint of your API on <api-host> and <api-port>. -i prints the status line, so you can see the result.

    Check: your API answers with an HTTP status in the 200 range.

    openshell sandbox exec --name "<sandbox-name>" --no-tty -- curl -sS -i "<api-url>"

    A failed token grant shows up as HTTP 502. If you see one, ask your administrator to look for the cause, for example a missing client for your sandbox.

  2. Look at the agent’s environment.

    Check: the environment holds no access token.

    openshell sandbox exec --name "<sandbox-name>" --no-tty -- env

Your agent reached your API with a fresh token, and it never held a secret. For the whole chain with a worked example, see Verify the setup end to end.
